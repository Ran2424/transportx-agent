## 结论摘要

当前模块的核心徐汇业务数据与所给原始数据是同一批来源，不是另一份独立数据。模块的构建元数据指向上级目录的 `data/traffic_governance.sqlite`；该数据库记录的 SHA-256 与本次实际计算值均为：

```text
85b12990652d43fc315a4620f6fedd922ef80f1507ba76bc78f7e4dc14b710aa
```

对公交、轨交、天气和道路四类原始事实逐项复算后，行数和核心汇总完全一致。模块的主要作用不是改变这些事实，而是：标准化时间和字段、统一实体 ID、转换已确认坐标至 WGS84、将网约车四源订单合并去重、预计算趋势/道路状态持续时间、记录质量状态，并额外接入静态网络和 EVDATA 道路速度。

因此，**同一事实、同一时间范围、同一口径的问数，结果应为 0 差异；口径未说明时，网约车问题可相差 0.02%--101.21%，道路和降雨问题甚至会因单位/聚合方法不同而不能直接比较。**

## 3. 模块做了哪些会影响答案的转换

### 3.1 网约车：四个来源合并为一份订单事实

原始目录将上车、下车、场馆离场和场馆到场分别存表。它们属于同一订单体系，不能相加后称为“订单数”。模块以订单号做并集、保留一个脱敏哈希订单，并从该订单派生端点和场馆事件。

| 指标 | 原始结果 | 模块结果 | 正确解释 |
| --- | ---: | ---: | --- |
| 上车表物理行数 | 641,479 | 原始上车端点 641,134 | 模块折叠 345 行源内重复，差 0.054% |
| 下车表物理行数 | 634,573 | 原始下车端点 634,446 | 折叠重复并排除 1 个无效端点，差 0.020% |
| 两表物理行数合计 | 1,276,052 | 原始上下车端点 1,275,580 | 差 472 行（0.037%） |
| 场馆两表物理行数合计 | 1,150,873 | 有效场馆到/离场事件 1,150,668 | 差 205 行（0.018%） |
| 四张订单表物理行数合计 | 2,426,925 | 有效唯一订单 `fact_trip` 1,206,193 | **不可同口径比较**；原始行数比唯一订单高 101.205% |
| 四源订单号并集（未过滤） | 1,206,222 | 有效唯一订单 | 1,206,193 | 仅 29 单因坐标越出上海合理范围而排除，差 0.0024% |
| 场馆订单号并集（未过滤） | 1,054,834 | 有效场馆唯一订单 | 1,054,805 | 同样仅排除 29 单，差 0.0027% |

场馆到场/离场的两个原始表中有 95,863 个订单号同时出现。若把两个表的行数直接当“场馆订单数”，会比模块的有效唯一场馆订单 **高 96,068 单（9.108%）**；这是“事件数”和“唯一订单数”混用，不是模块算错。

模块还提供 **2,269,148 个统一订单端点**，其中 **993,568 个**为场馆完整订单补齐的另一端点。它适合 OD、热点和完整行程分析，但不能拿来复现原始上/下车表的端点趋势；复现原表时应使用 `source_event_count`。

### 3.2 时间、ID 与字段

模块将业务时间统一按 `Asia/Shanghai` 解释，并派生：`date_key`（YYYYMMDD）、`minute_key`、15 分钟桶和小时。原始日期文本、轨交千分位客流字符串、道路状态小写代码等被标准化；这不会改变基础合计，但会让按小时/15 分钟、跨日行程和线路/站点关联的结果更稳定。

轨交客流仅覆盖 10 个物理站、19 个线路—站点组合；公交客流覆盖 75 条线路。模块新增的 420 个轨交站、20 条轨交线、151 条公交方向线路等主要是静态网络，**不能被误解为新增的全网客流覆盖**。

### 3.3 坐标与空间问答

原始网约车端点混有 GCJ-02、WGS84、BD-09、CGCS2000 等坐标标识；公交站点为 EPSG:32651。模块将已确认记录发布为 WGS84（EPSG:4326），并保留坐标质量状态。原始坐标若直接与 WGS84 场馆点做缓冲或距离计算，会产生明显的空间位置偏移；二者不应直接混用。

对场馆到/离场事件，模块有 1,681 条（0.146%）端点 CRS 未知，36,510 条（3.173%）按数据集多数证据推定为 GCJ-02 后转换。精确距离、500 米缓冲圈或热点排名应报告并按 `coordinate_status` 筛选；这类空间问题不能承诺与“未经坐标处理的原始 CSV”同值。

### 3.4 道路状态与降雨的聚合

原始道路表是“逢变更新”事件，不是等间隔状态快照。模块根据相邻事件推导状态持续时间；当前 190 个 `jam` 事件对应 **3,635.0 分钟**的严重拥堵持续时长。二者单位分别是“事件条数”和“路段分钟数”，不能比较为同一个“拥堵量”。

气象的“网格一小时累计降雨”是滚动一小时值。模块按网格—小时取最大值（或在明确需要时取平均），不逐条累加。本次原始数据中，非零降雨网格小时若误做逐条求和，最大会达到小时最大值的 **3 倍**，单个网格小时最高多报 **32.8 mm**。

## 4. 面向问答/问数的预期差异

| 问题类型 | 应使用模块对象/口径 | 与正确原始 SQL 的预期差异 | 主要风险 |
| --- | --- | --- | --- |
| “某日某线路公交交易/上客多少？” | `bus.fact_bus_line_30m` 或小时/日集市 | 0 | 把交易笔数说成乘客人数 |
| “某日某站进/出站客流多少？” | `metro.fact_metro_station_hour` | 0 | 将进出站合计称为去重客流，或外推为全网 |
| “某时段有多少网约车上车/下车事件？” | `mart_ridehail_event_*` 的 `source_event_count` | 约 0.02%--0.054% | 原始源内重复行；不可用 `event_count` 复现原表 |
| “当前样本有多少唯一网约车订单？” | `ridehail.fact_trip` | 相对四源订单号并集仅 -0.0024% | 把四张原表行数相加，结果会高 101.205% |
| “场馆到场/离场订单多少？” | 唯一订单用 `fact_venue_trip`；方向事件用 `fact_venue_event` | 过滤前后唯一订单仅 -0.0027% | 事件与订单混用可造成约 9.1% 偏差 |
| “某路段拥堵了多久？” | `road.mart_road_segment_hour/day` | 原始表没有现成可比值 | 把 `jam` 事件数当作拥堵时长 |
| “某网格某小时降雨多少？” | `common.mart_weather_grid_hour` | 取最大值时与正确原始算法一致 | 把滚动一小时雨量逐条相加，最高可 3 倍 |
| “场馆 500m 内有多少订单/哪个热点最高？” | WGS84 且 CRS 已知的 `fact_*` | 取决于 CRS 筛选，不能承诺为 0 | 原始 GCJ/WGS/BD 坐标混用造成空间偏移 |
| “场馆周边道路平均速度？” | `road.fact_evdata_road_speed_15m` | 原始徐汇文件夹无同口径结果 | 这是模块新增 EVDATA 数据；不能与 89 个状态发布段拼接 |

## 5. 建议的问答输出规则

1. 每次问数先明确“订单 / 端点事件 / 交易笔数 / 人次 / 路段分钟数”中的哪一种量纲；跨方式仅并列比较，不相加为综合客流。
2. 问网约车数量时默认回答唯一订单（`fact_trip`）；用户明确要求“原始上/下车表记录数”时，改用 `source_event_count` 并标注已去除源内重复。
3. 场馆问题需先问清是“唯一订单”还是“到/离场事件”。`BOTH` 订单可产生两个方向事件，但仍只是一笔订单。
4. 涉及距离、缓冲、空间热点时，必须说明使用 WGS84、剔除或单列 `UNKNOWN` 坐标，并说明 3.173% 的场馆事件坐标为多数证据推定。
5. 道路问题默认优先使用 EVDATA 的 15 分钟速度；若使用原发布段状态，输出“状态持续分钟数”而不是事件次数。两套路段 ID 尚未建立权威映射，禁止拼接。
6. 降雨按网格—小时最大滚动一小时累计值回答，不对分钟记录求和。
7. 所有回答都注明时间范围、实体覆盖和样本边界：本资产是徐汇/上海体育场相关样本，不能外推为上海全市总量。

## 6. 审计方法与限制

本次审计直接读取原始目录上级的 `traffic_governance.sqlite` 及当前安装模块的五个业务 SQLite 库，复算行数、订单并集、交易/客流合计、状态分布、质量结果和降雨聚合风险。未修改原始数据、模块数据库或项目代码。

结论只保证本次发现的原始库版本与已安装资产版本的关系。若 CSV/XLSX 或 `traffic_governance.sqlite` 被重新导入或更新，需重新校验 SHA-256、源表记录数和模块 `catalog.meta_build` 中的 `source_database_sha256`。
