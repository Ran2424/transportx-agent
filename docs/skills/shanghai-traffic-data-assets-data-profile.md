# 上海交通数据资产实际数据报告

数据目录：`skills/shanghai-traffic-data-assets/assets/databases`  
剖析日期：2026-07-30  
资产版本：`3.1.0`  
业务时区：`Asia/Shanghai`  
发布坐标系：`EPSG:4326`

治理与 SKILL 审查见[审查与优化报告](./shanghai-traffic-data-assets-review.md)。

## 1. 数据定位

本资产服务于“重大活动交通态势洞察及辅助决策智能体”，围绕徐汇区和上海体育场组织多方式交通数据，不是上海全市综合交通仓库。

- 轨交静态网络接近全网，客流只覆盖 10 个物理站。
- 公交静态数据覆盖 77 条官方线路和 151 条高德方向线路，不是上海全部公交。
- 原道路状态数据有 89 个发布段且没有几何；EVDATA 另有 207 个上海体育场周边 WGS84 几何路段。
- 订单主要覆盖场馆周边和所提供样本，不代表上海网约车总体。
- 天气只有 8 个徐汇网格。
- 数据库活动维表只有4个日期级标记；演唱会19:00—22:00的案例背景只在SKILL说明中维护，不进入订单数据。
- 各事实域约有 21—22 天数据，适合短期事件对比，不足以支撑季节性或年度趋势。

## 3. 时间、空间和 ID 标准

### 3.1 时间

| 字段 | 语义 | 示例 |
|---|---|---|
| `date_key` | `YYYYMMDD` 整数 | `20250823` |
| `minute_key` | 日内第几分钟，0—1439 | `1080` 表示 18:00 |
| `slot_15_start` | 15分钟桶起点 | `1095` 表示 18:15—18:29 |
| `hour` | 0—23 | `18` |
| `*_at` | Asia/Shanghai 本地时间文本 | `2025-08-23 18:15:00` |

### 3.1.1 SKILL 内置案例日程

| 日期 | 开始 | 结束 | 场馆 |
|---|---|---|---|
| 2025-08-20 | 19:00 | 22:00 | 上海体育场 |
| 2025-08-21 | 19:00 | 22:00 | 上海体育场 |
| 2025-08-23 | 19:00 | 22:00 | 上海体育场 |
| 2025-08-24 | 19:00 | 22:00 | 上海体育场 |

[上海地铁保障指南](https://www.jfdaily.com/sgh/detail?id=1627654)明确四日每日19:00—22:00；[上海市公安局公告](https://www.shanghai.gov.cn/nw31406/20250822/555caa8ba4894640ab88f64cbbf193ce.html)确认演出日和场馆。该日程只用于SKILL的分析背景，不写入订单事实。辅助决策默认观察15:00—19:00演前集结、19:00—22:00演出中、22:00—24:00散场。

订单按上车端和下车端分别保留日期和日内分钟，跨日行程不会被强行归到一个日期。

### 3.2 坐标

发布数据只有：

- `EPSG:4326`：可用于 WGS84 存储和跨域连接；
- `UNKNOWN`：保留记录，但不能做精确空间分析。

米制距离、缓冲和点线校验应投影到 `EPSG:32651`。`EPSG:3857` 只用于 Web 地图显示。

### 3.3 ID

- 轨交：统一 `line_id`、`station_id`。
- 公交：官方 `line_key`；来源站点用 `OFFICIAL:`/`AMAP:` 前缀。
- 订单：`order_hash`，不发布原始订单号。
- 空间对象：`geo_key`。
- EVDATA 道路：保留源 `road_id`；不与原状态发布段 ID 强行合并。

### 3.4 EVDATA 道路速度

用户提供的 `road_segment_80000.geojson` 与 `时代少年团数据.csv` 已接入道路分库：

| 项目 | 结果 |
|---|---:|
| WGS84 MultiLineString 路段 | 207 |
| 15分钟速度记录 | 14,977 |
| 时间覆盖 | 2025-08-24 00:00—23:45 |
| 全天 96 时槽完整路段 | 63 |
| 不完整路段 | 144 |
| `speed_avg > 120` 警告记录 | 12 |

CSV 与 GeoJSON 的 207 个路段 ID 完全一致，路段—时刻无重复。源文件没有声明
`speed_avg` 的单位，因此数据库使用 `speed_unit='UNKNOWN'`；高值保留原值并标记
`WARN_HIGH_SPEED`，不得在没有来源说明的情况下改写为 km/h。

## 4. 网约车订单与场馆订单

### 4.1 四类来源

| 代码 | 来源 | 原始业务含义 |
|---|---|---|
| `RHD` | 网约车上车表 | 一笔订单的上车端点 |
| `RHA` | 网约车下车表 | 一笔订单的下车端点 |
| `PFV` | 场馆离场订单表 | 与场馆离场相关的完整订单 |
| `PTV` | 场馆到场订单表 | 与场馆到场相关的完整订单 |

场馆表不是另一套交易系统。订单号回连结果如下：

| 统计 | 订单数 |
|---|---:|
| 上车/下车订单并集 | 1,179,655 |
| 场馆到场/离场订单并集 | 1,054,834 |
| 两个并集的交集 | 1,028,267 |
| 场馆订单重叠率 | 97.48% |
| 场馆来源独有订单 | 26,567 |
| 四源总并集 | 1,206,222 |

同时出现在两个场馆完整订单源的 95,863 个订单中，95,854 个核心字段一致，9 个存在时间或坐标差异。统一模型以场馆离场源为优先值，并保留 `venue_source_conflict=1`。

这意味着：

- 可以只保留一份订单标准层；
- 不能直接删除场馆表，因为它补充完整 OD、地点和场馆方向；
- 场馆订单应该作为统一订单的业务标签和派生视图；
- 把两个端点相加会得到事件数，不是订单数。

### 4.2 统一订单结构

`ridehail.std_trip` 一单一行，1,206,222 行，订单哈希全部唯一。

代表字段：

| 字段 | 用途 |
|---|---|
| `trip_key` | 本地技术键 |
| `order_hash` | 脱敏订单业务键 |
| `source_coverage` | 该订单出现在哪些来源 |
| `venue_relation` | `NONE/TO_VENUE/FROM_VENUE/BOTH` |
| `venue_source_conflict` | 两个场馆完整订单源的核心字段是否冲突 |
| `pickup_at`、`dropoff_at` | 上、下车时间 |
| `pickup_longitude/latitude` | 上车发布坐标 |
| `dropoff_longitude/latitude` | 下车发布坐标 |
| `pickup_crs`、`dropoff_crs` | `EPSG:4326/UNKNOWN` |
| `*_coordinate_status` | 坐标来源和推断依据 |
| `pickup_place`、`dropoff_place` | 来源地点文本；敏感，不建议默认输出 |
| `trip_duration_seconds` | 行程时长 |
| `source_duplicate_count` | 被折叠的源重复行 |
| `quality_status` | 整单质量 |

标准层质量分布：

| 状态 | 订单数 |
|---|---:|
| `OK` | 1,061,483 |
| `PARTIAL_TRIP` | 143,264 |
| `UNKNOWN_CRS` | 1,437 |
| `SOURCE_CONFLICT` | 9 |
| `INVALID_COORDINATE` | 29 |

有效订单事实 `fact_trip` 有 1,206,193 行。

### 4.3 场馆关系

有效订单中：

| `venue_relation` | 订单数 | 含义 |
|---|---:|---|
| `NONE` | 151,388 | 不在场馆来源中 |
| `FROM_VENUE` | 482,936 | 场馆离场 |
| `TO_VENUE` | 476,006 | 场馆到场 |
| `BOTH` | 95,863 | 同一订单同时命中到场和离场源 |

`fact_venue_trip` 是这些场馆关联订单的唯一订单视图，共 1,054,805 行。  
`fact_venue_event` 有 1,150,668 行；`BOTH` 订单会贡献一条到场事件和一条离场事件。

### 4.4 场馆 CRS 证据

离场事件的场馆端点是上车端；到场事件的场馆端点是下车端。

| 方向 | 回连 GCJ-02 | 回连 WGS84 | 回连 BD-09 | 无对应端点，按多数假设 GCJ-02 | 回连但未知 |
|---|---:|---:|---:|---:|---:|
| 离场 | 535,076 | 40,395 | 9 | 2,477 | 842 |
| 到场 | 525,097 | 11,893 | 7 | 34,033 | 839 |

结论：

- “大部分场馆订单是 GCJ-02”得到数据支持；
- “所有场馆订单都是 GCJ-02”不成立；
- 回连继承显式 CRS 比统一假设更稳妥；
- 无法回连的 36,510 个方向事件采用多数假设，字段明确标注；
- 1,681 个场馆方向事件回连到未知 CRS，不做强制转换。

### 4.5 端点来源

`fact_ridehail_event` 区分原始事件与场馆补齐端点：

| 端点 | 原始上/下车来源 | 场馆完整订单补齐 |
|---|---:|---:|
| 上车 | 641,134 | 478,484 |
| 下车 | 634,446 | 515,084 |

全部有效端点共 2,269,148；原始上/下车来源事件共 1,275,580。

查询时：

- 复现原始网约车事件趋势：用 `source_event_count`；
- 分析统一订单的全部端点：用 `event_count`；
- 订单量：用 `fact_trip`；
- 场馆到离场：用 `fact_venue_event` 或场馆集市。

## 6. 支持的分析级别

| 分析问题 | 能力 | 推荐对象 | 注意点 |
|---|---|---|---|
| 活动日多方式趋势 | 支持 | 各领域小时/日集市 | 单位并列，不求和 |
| 演前/演中/散场对比 | 支持 | SKILL案例日程 + 各领域小时事实/集市 | 默认窗口15—19、19—22、22—24；活动时刻不在数据库 |
| 场馆到场/离场波峰 | 支持 | `mart_venue_trip_15m` | 事件数不是唯一订单数 |
| 网约车原始事件趋势 | 支持 | `source_event_count` | 不含场馆补齐端点 |
| 完整订单 OD | 支持 | `fact_trip` | 仅用 EPSG:4326；说明推定状态 |
| 行程时长 | 支持 | `fact_trip`/场馆集市 | 排除部分订单和异常 |
| 轨交站小时客流 | 支持 | `fact_metro_station_hour` | 只覆盖 10 个站 |
| 公交线路小时/日客流 | 支持 | 公交集市 | 只覆盖 75 条客流线路 |
| 道路拥堵时长 | 支持 | 道路小时/日集市 | 没有几何 |
| EVDATA 演出日路段速度 | 支持 | `fact_evdata_road_speed_15m` | 单位未知；144 个路段时槽不完整 |
| 天气与交通时间关联 | 支持 | 天气小时集市 + 交通小时集市 | 天气按网格名称 |
| 全市客流总量 | 不支持 | 无 | 样本范围不足 |
| 长期季节性/年度预测 | 不支持 | 无 | 只有约三周 |
| 道路网络传播 | 不支持 | 无 | 原状态段缺几何；EVDATA 缺拓扑和权威映射 |

### 7.1 查看订单来源关系

```bash
/Users/ran/WorkSpace/SoftWare/miniconda3/envs/research/bin/python3.10 \
  "<Shanghai traffic query tools directory>/query_assets.py" --order-sources
```

### 7.2 某日场馆到离场小时趋势

```sql
SELECT date_key, hour, venue_relation,
       SUM(trip_count) AS venue_events,
       SUM(wgs84_trip_count) AS wgs84_events
FROM ridehail.mart_venue_trip_hour
WHERE date_key = 20250823
GROUP BY date_key, hour, venue_relation
ORDER BY hour, venue_relation;
```

### 7.3 区分原始网约车事件和补齐端点

```sql
SELECT date_key, hour, event_type,
       SUM(source_event_count) AS source_events,
       SUM(venue_enriched_event_count) AS venue_enriched_endpoints,
       SUM(event_count) AS all_endpoints
FROM ridehail.mart_ridehail_event_hour
WHERE date_key = 20250823
GROUP BY date_key, hour, event_type
ORDER BY hour, event_type;
```

### 7.4 活动日道路状态

```sql
SELECT m.date_key,
       SUM(m.jam_seconds) / 60.0 AS jam_minutes,
       SUM(m.crowd_seconds) / 60.0 AS crowd_minutes
FROM road.mart_road_segment_hour m
JOIN common.dim_event e ON e.event_date_key = m.date_key
GROUP BY m.date_key
ORDER BY m.date_key;
```

## 8. 查询前检查

每次分析先确认：

1. 当前要统计订单、端点还是场馆业务事件；
2. 使用的时间粒度；
3. 数据覆盖是否与问题范围一致；
4. 缺失记录是零还是未观测；
5. 坐标是否为 EPSG:4326；
6. 是否接受数据集多数推定的场馆坐标；
7. 输出是否包含不必要的精确地点、时间或坐标。
