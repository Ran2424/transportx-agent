# 上海交通数据资产 SKILL 审查与优化报告

审查对象：`modules/official/traffic-data/skill`
审查日期：2026-07-23  
优化后版本：`3.1.0`  
数据标准：`Asia/Shanghai`、`EPSG:4326`

配套数据报告：[上海交通数据资产实际数据报告](./shanghai-traffic-data-assets-data-profile.md)

## 1. 结论

2026-07-30 补充：新增 EVDATA 道路资产，包括 207 个 CRS84/WGS84 路段和
2025-08-24 的 14,977 条 15 分钟平均速度记录。该来源使用独立 `road_id`，
未与原 89 个道路状态发布段强行映射；源速度单位未声明，目录中登记为 `UNKNOWN`。
144 个路段时槽不完整、12 条大于 120 的高值均以警告保留。

本资产明确服务于“重大活动交通态势洞察及辅助决策智能体”，以上海体育场时代少年团「加冠礼」演唱会—「冠军」上海站为内置案例。本次审查完成了数据模型、构建脚本、查询接口和 SKILL 说明的同步修改。

案例包含4场演出：

| 日期 | 开始 | 结束 |
|---|---|---|
| 2025-08-20 | 19:00 | 22:00 |
| 2025-08-21 | 19:00 | 22:00 |
| 2025-08-23 | 19:00 | 22:00 |
| 2025-08-24 | 19:00 | 22:00 |

时间依据为[上海地铁发布的演唱会保障指南](https://www.jfdaily.com/sgh/detail?id=1627654)；[上海市公安局公告](https://www.shanghai.gov.cn/nw31406/20250822/555caa8ba4894640ab88f64cbbf193ce.html)确认了演出日期和场馆。这些活动背景只写入 SKILL 说明，不进入 `ridehail.std_trip`、订单事实或订单集市。2025-08-23邻近上海体育馆还有UFC赛事，当天交通变化不能全部归因于演唱会。

最重要的结论是：网约车上车/下车数据与场馆到场/离场数据属于同一订单体系。场馆订单并集有 1,054,834 个订单，其中 1,028,267 个也出现在网约车上车或下车表中，重叠率为 97.48%。原来的两套事实模型会重复存储和重复计数，已经改为一套统一订单事实：

- 四类来源合并到 `ridehail.std_trip`，一单一行；
- `ridehail.fact_trip` 负责订单、OD 和行程时长；
- `fact_ridehail_event` 从订单拆出上下车端点；
- `fact_venue_trip` 是场馆订单子集；
- `fact_venue_event` 派生场馆到场和离场事件；
- 15分钟、小时和日集市服务常规查询。

同时命中场馆到场、离场两个来源的 95,863 个订单中，95,854 个核心行程字段一致，9 个存在冲突。统一订单对这 9 个记录采用场馆离场源优先，并设置 `venue_source_conflict=1`，没有静默覆盖。

统一后，`std_trip` 有 1,206,222 行，`COUNT(*)` 与 `COUNT(DISTINCT order_hash)` 相等，也与四源订单号并集一致。

## 2. 已完成的优化

### 2.1 统一时间标准

- 业务时区登记为 `Asia/Shanghai`。
- 日期统一为 `date_key=YYYYMMDD`。
- 日内时间统一为 `minute_key=0—1439`。
- 增加或完善 15 分钟、小时和日业务集市。
- `common.dim_event` 保持原有日期级标记，不向订单层增加活动字段。
- SKILL 说明给出四场19:00—22:00的案例背景和默认分析窗口。

### 2.2 统一坐标标准

发布资产的唯一标准坐标系为 WGS84，即 `EPSG:4326`。

已确认的坐标均完成转换：

- 高德公交和轨交 GCJ-02 点线；
- 官方公交站 EPSG:32651；
- 网约车 GCJ-02、WGS84、BD-09；
- 用户确认的上海体育场 WGS84 坐标。

发布表不再保留另一套源坐标列。无法确认 CRS 的记录继续保留，标为 `UNKNOWN`，并在字段和文档中说明不得用于精确空间分析。本次 `PUBLISHED_CRS_STANDARD` 规则通过，未发现非法 CRS 值或遗留源坐标副本列。

### 2.3 场馆订单 CRS 反推

场馆订单本身没有 CRS 字段，不能直接把全部记录认定为 GCJ-02。本次按订单号回连上车表和下车表：

- 能回连时，继承同订单对应端点的显式 CRS；
- 回连结果为未知标识时，记录保留为 `UNKNOWN`；
- 无法回连时，才依据数据集多数为 GCJ-02 的证据进行推定。

这一处理避免了一个实际错误：场馆离场订单回连上车表后，约 7% 的记录明确标为 WGS84。如果无条件按 GCJ-02 转换，这部分坐标会被二次偏移。

所有推断都有字段标识，例如：

- `INFERRED_GCJ02_FROM_MATCHED_DEPARTURE`
- `INFERRED_WGS84_FROM_MATCHED_ARRIVAL`
- `ASSUMED_GCJ02_FROM_DATASET_MAJORITY`
- `UNKNOWN_CRS_FROM_MATCHED_DEPARTURE`

### 2.4 业务聚合

补齐了常用业务层：

| 领域 | 小时 | 日 |
|---|---|---|
| 公交 | `mart_bus_line_hour` | `mart_bus_line_day` |
| 轨交 | 小时事实 | `mart_metro_station_day` |
| 道路 | `mart_road_segment_hour` | `mart_road_segment_day` |
| 天气 | `mart_weather_grid_hour` | `mart_weather_grid_day` |
| 订单端点 | `mart_ridehail_event_hour` | `mart_ridehail_event_day` |
| 场馆事件 | `mart_venue_trip_hour` | `mart_venue_trip_day` |

订单和场馆事件另有 15 分钟集市。这样 Agent 无需扫描 120 万行订单即可回答大多数趋势问题。

### 2.5 查询接口

`query_assets.py` 新增：

- `--coverage`：领域覆盖、粒度、CRS 和使用限制；
- `--business`：可用集市；
- `--order-sources`：网约车与场馆订单的并集、重叠率和解释。

同时增加只读 SQL 前缀校验、对象名校验和最大返回行数限制。

### 2.6 SKILL 说明

SKILL 已明确写入：

- Agent 的发现顺序；
- 订单、事件、场馆子集的区别；
- `source_event_count` 与 `event_count` 的区别；
- 时间和坐标契约；
- 场馆 CRS 推断证据；
- 每次分析必须报告的覆盖、粒度、单位和 CRS。

### 2.7 分库数据字典

保留 `coverage.md`、`schema.md`、`spatial.md`、`metrics.md` 和 `governance.md` 五份整体说明，并新增六份按需加载的数据库 Reference：

- `catalog.md`：目录、血缘、质量、指标和查询发现；
- `common.md`：公共日期、时间、活动日期、场馆和天气；
- `road.md`：道路状态事件及小时、日集市；
- `metro.md`：轨交线路、站点、映射、客流和采集质量；
- `bus.md`：公交线路、方向、站序、交易和采集质量；
- `ridehail.md`：统一订单、端点、场馆事件和聚合集市。

每份分库文档均列明实际表、行数、粒度、全部字段、连接规则、分析边界和查询样例。Agent 可以先通过 `catalog` 发现对象，再只读取与当前问题相关的分库文档。

## 3. 逐项审查

### 3.1 数据发现

状态：已改善。

`catalog.meta_analysis_guide` 提供领域级推荐对象和限制，`meta_order_source_relation` 提供订单来源关系。Agent 不再需要读完整 schema 才能判断从哪张表开始。

仍可提升：

- `meta_column` 目前主要是技术字段字典，缺少字段级中文定义、单位、敏感级别和可空原因。
- 质量规则只保留本次结果，没有历史趋势。

### 3.2 粒度管理

状态：已形成清晰层次。

- 原始业务粒度得到保留；
- 常用小时和日聚合已建立；
- 订单和端点不再混为同一粒度；
- 场馆 `BOTH` 订单可能产生两个业务事件，但仍是一笔订单。

仍可提升：

- 后续若增加空间网格集市，需要先明确网格尺度和隐私阈值，不宜直接发布精确 OD 聚合。
- 缺失时段仍表示未观测，不能自动补零；后续可增加完整性指标。

### 3.3 坐标管理

状态：已达到统一发布标准。

空间分析前只需检查 `crs` 和 `coordinate_status`，不再在多套坐标字段中选择。米制分析仍应投影到 EPSG:32651。

未解决的问题：

- 8 个天气网格 CRS 未确认；
- 1 个轨交站缺坐标；
- 原 89 个道路状态发布段没有几何；EVDATA 的 207 个几何路段尚未与其建立权威映射；
- 场馆订单中有 36,510 个有效方向事件采用数据集多数假设，需要在高精度分析中单独评估。

### 3.4 数据质量

状态：错误级规则全部通过。

保留的警告：

- 1 个轨交站缺坐标；
- 1,684 个订单端点 CRS 未知；
- 29 个场馆关联订单坐标异常；
- 9 个双场馆源订单核心字段冲突；
- 4 条数据库活动记录只有日期；演出时间只在 SKILL 案例说明中维护。

事件采用端点级质量过滤，订单采用整单质量过滤，避免一端异常把另一端有效的原始事件一并删除。

### 3.5 隐私

状态：订单号已假名化，但明细仍属敏感数据。

已完成：

- 原始订单号不进入 Agent 数据库；
- 四源合并只使用 SHA-256 哈希；
- 常规查询提供 15 分钟、小时和日集市。

仍需控制：

- 精确时间、坐标和地点文本可形成稳定轨迹；
- 对外提供结果时应使用最小必要字段；
- 如果需要更广泛分发，应增加空间网格化、最小样本阈值和地点文本脱敏，而不是只依赖哈希。

### 3.6 构建与发布

状态：可重复构建，生成数据库仍由本地受控安装包管理。

构建记录了源库哈希、源库大小、Python 路径、标准 CRS、标准时区和构建时间。Git 忽略数据库和原始治理库。

待改进：

- 构建约需数分钟，主要成本是 240 万个订单端点的坐标转换。可在后续引入受控的批量向量化，但没有必要为日常查询复杂化当前实现。
- 构建仍是覆盖式，应继续只在用户明确授权时执行。

## 4. 推荐后续工作

### P0：查询安全与准确性

1. 为 `meta_column` 增加中文定义、单位、敏感级别、允许空值原因。
2. 为订单明细查询增加默认最小化示例，避免 Agent 输出地点文本和精确坐标。
3. 在现有构建后断言基础上，继续增加原始源订单并集和日期覆盖回归测试。

### P1：分析能力

1. 取得天气网格 CRS 说明并转换到 WGS84。
2. 建立原道路状态发布段、EVDATA 路段与权威道路网之间的映射。
3. 后续取得正式开门、交通管制起止和疏散结束时间后，再更新SKILL中的演前/散场分析窗口。
4. 根据实际业务决定是否增加匿名空间网格集市，例如 250 米或 500 米；先确定隐私阈值。

### P2：治理闭环

1. 保存质量结果历史，而不是只保留最近一次。
2. 增加构建清单和文件哈希，便于安装包核对。
3. 为 CRS 推断规则增加版本号和证据摘要。
