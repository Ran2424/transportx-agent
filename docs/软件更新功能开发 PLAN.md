# TransportX Agent 软件更新功能开发计划

日期：2026-10-08。状态：待实施。本文件描述后续开发方案，不代表在线更新已经上线。

## 1. 目标与实施顺序

让已安装的桌面客户端通过应用内入口发现新版本、查看说明、下载安装包，并在用户确认且任务空闲后重启安装。升级保留用户数据，下载或检查失败不影响当前版本使用。

实施分为两条链路：先完成主程序在线更新及发布流程，再接独立 Module 更新。首版仅支持现有发布平台 macOS arm64 和 Windows x64、stable 通道；不加入强制更新、代码热替换、多通道切换或自动降级。

成功标准：使用正式发布形态的两个连续版本，在两种系统上完成“发现新版 → 下载 → 重启安装 → 新版启动”，并验证会话、模型配置、认证、工作区及已安装模块保留。

## 2. 已有基础与缺口

| 项目 | 当前情况 | 后续工作 |
|---|---|---|
| 下载服务 | 上海 OSS Bucket `transportx-agent`，标准存储、同城冗余；HTTPS 下载域名 `download.transkgllm.com` 已验证 | 增加更新目录、缓存规则和发布脚本 |
| 安装包 | v3.22.0 Mac DMG、Windows EXE 与 SHA-256 文件已上传 `releases/v3.22.0/` | 保留作为手动安装入口，不把已有文件覆盖成新版本 |
| 官网 | 中英文产品页的下载地址已切换到 OSS | 每次发布同步版本、大小、下载及校验链接 |
| 桌面打包 | electron-builder 26.15.3；Mac 仅 DMG，Windows NSIS | 加入 `electron-updater`、publish 配置和 Mac ZIP |
| 更新客户端 | 尚无更新器及对应 IPC | 增加主进程更新服务和工作台入口 |
| 桌面退出 | `main.ts` 的 `before-quit` 等待 supervisor 停止后调用 `app.exit(0)` | 区分普通退出与更新安装，避免绕过更新器安装生命周期 |
| Agent Host | supervisor 管理进程；服务端已有 shutdown，终止分析、视频与 Pi 会话 | 增加安装准备与执行状态核验，验证停止流程的确认方式 |
| 用户数据 | 独立于应用目录，路径按平台解析 | 原位保留，仅在格式变化时引入迁移 |
| Module | 已有按 `<id>/<version>` 安装、兼容性检查和会话精确版本冻结 | 后续增加远端目录与下载，复用已有安装器 |

当前 Mac v3.22.0 采用 ad-hoc 签名，未公证。HTTPS 证书只保护下载连接，不是应用代码签名证书。不能将当前安装包直接宣称为可自动更新的正式签名版本。Windows 包的实际签名状态也须在对应系统验收。

基础架构以 [ARCHITECTURE.md](ARCHITECTURE.md) 为准；本计划不改变 Electron → Node Agent Host → React 的边界。

## 3. 更新边界与职责

| 层 | 职责 |
|---|---|
| Electron 主进程 | 维护更新状态，调用更新器，核验 IPC 来源，协调安装前退出 |
| preload | 暴露固定的检查、下载、安装、读取状态及订阅接口；订阅返回清理函数 |
| React 工作台 | 展示当前版本、更新说明、下载进度、失败与重试入口，提交用户操作 |
| Node Agent Host | 提供运行状态、进入更新准备状态、完成持久化和受控停止 |
| 发布脚本 | 校验产物、上传文件、验证下载、最后发布清单 |
| OSS | 保存公开发布文件，通过 HTTPS 提供下载；不承载用户配置或认证 |

主程序更新整体替换 Electron、React、Node 服务、内置 Pi/Python 及内置模块，避免同一客户端内混用不同平台版本。独立安装的 Video Capability、知识库等 Module 不随主程序更新自动重装。

Web/CLI 模式继续按现有部署或安装方式更新；缺少桌面 bridge 时不显示桌面安装操作。更新器只在已打包应用启用；本地开发测试源显式配置，不进入正式包。

## 4. 下载源与发布布局

保留已有 `releases/` 下载目录；新增以下更新目录，路径仅为拟定约定，尚未创建：

```text
releases/v<version>/                 # 官网手动下载安装包、校验值、说明
updates/stable/mac-arm64/            # generic provider 基础 URL
  latest-mac.yml
  <带版本号的 DMG、ZIP 与构建生成的 blockmap>
updates/stable/win-x64/
  latest.yml
  <带版本号的 NSIS EXE 与构建生成的 blockmap>
```

固定更新源分别为 `https://download.transkgllm.com/updates/stable/mac-arm64/` 和 `https://download.transkgllm.com/updates/stable/win-x64/`。由打包配置写入应用内 `app-update.yml`；平台与架构映射集中在 `desktop/scripts/platform-profile.mjs`，不在业务代码增加平台判断。

首版把更新清单引用的文件放在同一更新目录，直接保留构建输出中的相对文件名，避免手工改写清单。手动下载目录需要相同文件时，可在 OSS 内拷贝；发布记录列出全部目标对象。

清单由 electron-builder 生成，更新器按清单中的 SHA-512 校验下载文件。SHA-256 文件继续供手动下载核验，不代替更新器校验。HTTPS 与应用签名共同构成发布边界，不能仅靠同源哈希证明发布者身份。

- 带版本号的包发布后不可覆盖，使用长缓存；修复必须提升版本。
- `latest*.yml` 使用 `Cache-Control: no-cache`，要求重新验证；若接 CDN，单独设短缓存或不缓存并刷新清单。
- 保留清单引用的当前及历史包和 blockmap；清理前确认差分下载对旧版本文件的需求，不按天数直接删除。
- 发布文件允许匿名 GET/HEAD 与 Range 下载；上传仍需发布身份认证。现有 Bucket 默认 ACL 为私有，发布脚本须显式设置发布对象公共读，不依赖 Bucket 默认权限。
- 保留 OSS 当前公共访问设置，发布脚本遇到权限或公共访问拦截应报错，不自动修改账号全局安全开关。

## 5. 主程序更新流程

默认 `autoDownload=false`、`autoInstallOnAppQuit=false`。用户普通关窗或退出不触发安装；仅明确点击“重启并更新”后进入安装流程。

启动并加载工作台后后台检查一次，设置页可手动检查；同一轮检查去重，不轮询下载源。关闭设置页不取消下载，重新打开通过状态快照恢复展示。

```text
idle → checking → available / up-to-date
available → downloading → downloaded
downloaded → preparing → installing → 新版本重启
检查或下载失败 → error → 用户重试
准备失败或任务忙碌 → 保留 downloaded，继续使用当前版本
```

状态至少包括当前/目标版本、阶段、下载进度、可展示错误、更新说明和安装可用性。重启后从更新器核验的缓存及当前版本恢复状态，不仅依赖 React 内存。版本显示使用实际应用版本，不能由网页硬编码。

更新说明使用纯文本或现有安全 Markdown 渲染；渲染层不能提交任意更新 URL、文件路径或 shell 命令。IPC 必须校验请求来自当前工作台 webContents，并拒绝重复安装、错误阶段的操作。处理订阅卸载、窗口销毁和重复初始化。

### 安装前协调

1. 用户点击安装，主进程向 Agent Host 请求进入更新准备状态；检查 Pi 生成、工具任务、视频/空间分析、模块安装和文件写入是否进行中。
2. 若有进行中的工作，返回原因并保持当前版本；首版要求用户等待或自行停止，不后台强制终止任务，不自动预约安装。
3. 空闲时锁住新任务和写操作入口，完成待持久化操作，确认已保存。忙碌判断与锁定要在 Host 侧协调，不能只依赖前端状态。
4. 等待 Agent Host 受控退出，确认相关子进程停止，再调用更新器安装入口。
5. 区分“为安装而停止”与意外退出，避免 supervisor 弹出启动失败提示。安装准备超时、保存失败或无法确认停止时中止安装，报告原因并恢复工作台；若 Host 已停止则按需要重启它。

现有 shutdown 包含强制超时退出，不能据此认为数据已经保存；实施时需验证 Utility Process 的停止行为和 Host 确认消息。更新流程不能在调用 `quitAndInstall()` 前执行 `app.exit(0)`，也不能重复进入 `before-quit` 死循环。为普通退出与安装退出建立一个最小、可测试的协调路径，不重写整个 supervisor。

## 6. 签名、首次接入与恢复

macOS 正式更新要求 Developer ID 签名，并按现有发布规则公证；新增 ZIP 更新包，DMG 保留给首次安装。Windows 正式包沿用 Authenticode 与可信时间戳，保留更新签名验证。具体行为锁定在与 electron-builder 26 配套的更新器版本上验证，不照搬后续大版本文档。

签名身份、appId、安装路径与产品名应保持连续；当前发布文件的展示名含不同标点，需固定后续 artifact 命名，并验证安装器识别同一个应用。没有正式签名条件时，可完成代码和本地测试，但不开放正式更新清单；继续提供手动下载安装入口。

v3.22.0 不包含更新客户端，需要用户手动安装一次“支持更新的首版”，以后才能应用内更新。首版版本号在发布时确定；从旧 ad-hoc Mac 版本迁移应验证手动替换安装和用户目录保留，不能假设能够无缝自动更新。

更新失败处理：

- 检查/下载失败：当前应用继续运行，提供重试和官网手动下载入口。
- 校验或签名失败：禁止安装，记录不含凭据的诊断日志。
- 安装后启动失败：依靠保留的历史安装包进行人工恢复；首版不承诺自动回滚。
- 线上发现坏版本：撤回清单可阻止尚未更新的客户端发现它，但已升级的客户端需更高版本修复，不能把旧清单当作自动降级方案。

## 7. 数据与会话兼容

`desktop/app-paths.ts` 继续解析用户目录，不将更新缓存、凭据或用户数据写进应用包。保留 `scenario/`、`sessions/`、`modules/`、模型与认证配置、settings 和日志；不修改已有会话的 Resolved Session Plan。

若更新涉及数据格式变化，按需增加有版本、可重复执行的迁移：先备份需修改的文件，检查旧格式，再进行原子替换；迁移失败时保留备份并给出恢复说明。没有格式变化的版本不增加迁移层。人工降级前必须确认旧版能读取新版数据。

内置 Module 被新应用替换后，旧会话冻结的版本未必仍可解析。每次发布必须验证旧会话恢复：不兼容时阻止静默替换、说明所缺版本；若产品要求继续执行旧会话，则单独设计受控保留旧内置模块的方案，不能把兼容性自动归因于独立用户目录。独立已安装模块的历史版本继续保留，不因主程序更新删除。

## 8. 实施阶段与验收

| 阶段 | 交付 | 验收标准 |
|---|---|---|
| P0：约定与前置条件 | 固定更新路径、命名和签名身份，核实发布证书、旧版迁移和 Host 空闲判断 | 两平台产物要求明确；区分可自动更新与仅手动下载版本 |
| P1：打包与发布 | 加入更新器依赖、publish 配置、Mac ZIP；新增 `release:oss` 命令 | 清单引用的文件、版本、架构、SHA-512 一致；上传失败不改变线上清单 |
| P2：桌面更新核心 | 更新状态、受控 IPC、检查/下载/手动安装、退出协调 | 重复操作去重；错误不影响当前版本；忙碌与保存失败禁止安装 |
| P3：工作台入口 | 设置页版本区、说明、进度、重试和重启按钮，中英文文案 | 桌面可完成操作；Web 无安装按钮；三主题符合 semantic token 和字号纪律 |
| P4：实际升级与首发 | 两个平台旧/新版本安装测试、发布文档与手动迁移说明 | 从含更新器的旧版升级到新版，数据保留且 Host 正常启动；普通退出不安装 |
| P5：独立模块更新 | 远端目录、兼容投影、下载和现有安装器衔接 | 同 ID 新版并存，已有会话保持原精确版本；错误包不落入正式模块目录 |

P0–P4 作为一个功能分支按上述顺序交付，通过 PR 合并；P5 单独设计和 PR。当前只编写计划，不安装更新器、上传更新清单或修改用户运行配置。

拟修改位置：

- `desktop/update-service.ts`（新增）、`desktop/main.ts`、`desktop/preload.ts`：更新与生命周期。
- `src/contracts/`：更新状态及 IPC 数据契约，沿用现有契约组织方式。
- `src/server/server-main.ts` 及已有会话/任务服务：更新准备、忙碌和持久化确认。
- `src/web/platform/settings/SettingsDialog.tsx` 及对应样式、国际化：更新入口。
- `desktop/scripts/platform-profile.mjs`、electron-builder 配置：平台更新参数及产物。
- `desktop/scripts/publish-oss.mjs`（新增，名称实施时确定）：编排官方 ossutil，校验明确的文件列表。
- `package.json`、锁文件、测试、`docs/CHANGELOG.md` 和发布说明：依赖、命令及维护记录。

不在业务代码新增 `process.platform` 分支或 `.exe` 拼接，不手工编辑构建生成的 runtime manifest。仅增加契约时不提高 Module 版本；实际修改 Module 时按模块版本纪律同步提升 manifest 与 CHANGELOG。

## 9. 发布操作与检查

1. 同步 `package.json` 与 `PLATFORM_VERSION`，将待发布变更移入对应版本 CHANGELOG。
2. 在各自平台使用同一源码提交构建正式签名包；Windows 不在 Mac 上交叉打包。产物保留源码提交、依赖锁定与 runtime manifest 信息。
3. 运行 `release:oss` 预检/试运行：限定发布版本和 profile，拒绝缺失、混合版本、错误架构与同版本包覆盖，保留发布记录。上传命令不得扫整个 `release/`，避免旧包混入。
4. 上传全部版本文件与校验值，设置公共读及文件缓存属性；使用匿名 HTTPS HEAD/Range 验证可访问与大小，结合本地哈希及 OSS 上传完整性校验，预检清单的所有引用。
5. 文件验证通过后，最后替换该平台的 `latest*.yml`；记录旧清单供撤回。不同平台独立清单，只开放已验收平台，不声称跨平台发布是原子事务。
6. GitHub Releases 保留同一份资产及说明，官网仓库更新相应下载地址；无需用户为下载配置 GitHub 访问。
7. 从已安装客户端检查线上版本并完成一次升级；复核日志、用户数据与模块版本。

发布凭据使用限定 Bucket/前缀的 RAM 权限，保存在本地发布环境或 CI secret，不写进仓库、安装包和前端；按上传、分片、校验及设置对象 ACL 的实际操作授予权限。CI 采用单发布任务串行化，避免同平台清单相互覆盖。

## 10. 测试与运行维护

先运行 `npm run test:budget`，新增场景合并到已有 case/套件，`test/suites/*.test.ts` 不超过 40 个。单元/集成测试使用可控更新源，不下载真实大包；OS 安装能力另用真实产物验证。

| 场景 | 必须验证 |
|---|---|
| 更新状态与 IPC | 无新版、重复检查、未下载就安装、非工作台请求、订阅清理 |
| 网络与文件 | 清单 404/403、断网、下载中断、错误哈希、包缺失、错误架构、签名拒绝 |
| 任务与退出 | 更新准备后拒绝新工作；忙碌、保存失败及停止超时不安装；普通退出不安装 |
| 安装与重启 | Mac ZIP 更新；Windows NSIS 原位更新；无重复 Host 或残留子进程 |
| 数据兼容 | 认证不丢失、不出现在日志；工作区、历史会话、模块精确版本及迁移备份 |
| 发布 | 文件上传失败不发布清单；清单可刷新；已发布包不覆盖；旧版仍可下载 |

检查命令按改动范围运行 `npm run typecheck`、`npm test`、`npm run test:web` 和对应 `test:platform:macos/windows`。需要新增真实跨版本升级步骤，现有平台启动冒烟不能替代升级验收。

日志记录版本、阶段、错误码和必要的请求 ID，不记录认证、下载签名参数或用户任务内容。检查版本不携带用户文件、会话和模型配置。免费 HTTPS 证书到期前须重新签发并部署；配置证书有效期、发布错误和流量/费用告警。

首版按用户点击下载控制流量。OSS 直连会按实际传输量收费，重试与完整包回退可能增加成本；blockmap 存在不代表两平台每次都能差分更新。CDN 和流量包在下载量稳定后单独评估，不作为首版开发前置条件。

## 11. 独立 Module 更新的后续约束

P5 在 OSS 增加目录清单，列出模块 ID、精确版本、平台/架构、平台兼容范围、包 URL、大小、SHA-256 和说明；为目录建立发布者可信校验方案，不仅下载一个可任意执行的 ZIP。

用户选择新版后下载至受控暂存区，交给现有 `module-installer.ts` 的导入、预览与安装流程，继续拒绝符号链接、路径逃逸、内置 ID 冲突和不兼容 native runtime。安装成功后刷新能力投影；新会话使用用户选择的新版，旧会话保持原版本。

不得覆盖旧目录或自动卸载冻结会话引用的版本。主程序不兼容时提示先更新平台；不能在 Pi 正在执行时切换 Extension。模块网络更新应复用现有鉴权 API 和投影边界，不另建模块安装后台。目录格式、信任机制和清理策略在 P5 实施前单独评审。
