## 1. 目标、范围与首版完成定义

### 1.1 产品目标

交通仿真是 TransportX 的可安装、按任务选用的交通建模与方案实验能力，拟沿用 Module ID `com.transportx.traffic-simulation`。长期可以扩展道路交通、公共交通和共享出行等问题；本期以虹桥枢纽夜间多方式疏散与接续交付，比较公交、地铁、网约车及接驳组合下的运力、班表、分流和入场控制方案。

通用部分负责场景输入、变体、Run、结果与实验条件，首版运营模型负责旅客、队列、服务和车辆周转；虹桥数据包提供地点、日期和组织规则。通用执行接口不要求每个场景都有疏散点、末班车或旅客队列，也不因首个样例来自虹桥而写死地名、点位数和线路数。长期产品方向不表示当前已经支持全部交通方式或城市级模型。

“多方式联合”同时包括：

- **并行分担**：同一时段、不同目的地方向的客流分配给公交、地铁、网约车等服务。
- **连续接续**：同一旅客通过“接驳公交 → 地铁”“接驳公交 → 外围网约车”等出行链完成运输。每段必须校验到达时刻、换乘耗时、服务时段与可用容量。

输入是实际道路、疏散点、接驳点、线路、排班/时刻表、车辆供给与到达需求；输出是逐人服务过程、逐车运行、节点积压、出行完成情况及方案比较。Agent 组织实验、调用工具并解释结果；确定性代码执行交通规则和调度策略，不由模型逐仿真步决策。

### 1.2 微观范围与边界

| 对象 | 首版表示 | 需要保留的约束 |
|---|---|---|
| 道路车辆 | SUMO 逐车微观运行 | 实际车道、连接、转向、信号、跟驰/换道与背景交通；排队和回溢影响运行时间 |
| 公交/接驳车 | 每辆车、每班次、每次服务 | 实际路线/站序、容量、上客泊位、上下客时间、发车规则、车辆多趟周转 |
| 网约车 | 每辆车、每个订单/出行组 | 供给、匹配、驶入、候车、上客、离场和再次可用时间；车辆队列与旅客队列分开 |
| 地铁 | 按班次提供的运输服务 | 到发时刻、停站、剩余运能、首末班/加班车和后续接续，不模拟列车信号与折返动力学 |
| 疏散点/接驳点 | 逐人排队与离散服务事件 | 分方向队列、候车容量、泊位占用、服务顺序、满载滞留与下游接收能力 |
| 行人 | 点间步行连接或到达时间分布 | 换乘距离/耗时、必要的过街等待；不模拟站厅、站台、楼梯和室内人群避让 |
| 铁路/航班到达 | 外生客流到达过程 | 按实测或明确假设的批次、时刻、人数与目的地方向进入疏散点 |

采用“道路微观 + 节点离散事件”的混合模型。道路范围按疏散线路与拥堵影响确定；关键道路/出入口/接驳点周边保留微观细节，远端可使用有来源的分时旅行时间。越过微观路网边界只表示离开该区域，不能自动记为到达最终目的地；外部行程、返程耗时与后续接续仍需记录。

首版不包含枢纽室内行人仿真、全市交通均衡、逐步自然语言控制、运行中任意改网、强化学习或全局自动最优调度。地铁班次模型不生成未经计算的列车位置动画。

### 1.3 首个闭环与完成标准

固定样例包含：一个疏散点、一个外围接驳点、两个目的地方向；公交接驳与网约车分担，接驳点衔接具有末班时刻和容量限制的地铁。使用可分发的固定路网、班表和明确标为合成的需求，不以在线取数为前置条件。

两套方案使用共同的到达需求与目的地需求，只改变声明的运力、班表、分流或入场控制规则。用户能够：

1. 查看输入及缺失项，冻结场景并创建方案变体。
2. 启动受管无头 Run，在专属 Simulation Canvas 中观看节点、车辆和线路的状态变化。
3. 暂停观看、拖动已计算区间、调整播放速度，查询对应时刻的队列与服务记录。
4. 比较离开枢纽和完成整条出行链的结果，识别满载、错过末班、车辆周转不足与接驳点积压。

道路限速对照可保留为底层检查，不再作为产品首版的验收主线。样例跑通只证明执行与规则闭环；真实虹桥收益需要独立校准和验证。

另用同一执行链运行一个无疏散节点、无乘客服务的最小道路样例，验证场景、Run、轨迹和道路指标不依赖疏散模型。这是小型复用检查，不另建道路产品、编辑器或完整验收项目；不以共享单车或第二座城市的实现作为首版前置。

### 1.4 能力范围与扩展准入

| 范围 | 本期承诺 | 后续扩展条件 |
|---|---|---|
| 道路、公交、网约车、轨道班次服务、点间步行 | 按 1.2 节的精度支持首版疏散；道路最小样例检验通用执行链 | 每种方式分别列明运行模型、运营规则、状态权威及数据需求 |
| 其他城市/枢纽、多种班表和节点组织 | 通过有版本的输入和规则配置适配，不硬编码虹桥 | 具体项目的数据、规则与模型有效性另行验证，不默认参数可迁移 |
| 自行车、共享单车、需求响应公交 | 不作为本期开发任务；不预建空接口或能力插件 | 有独立用例后补网络/设施、库存借还、匹配/调度等模型与守恒验收；增加车型不等于支持运营 |

同一仿真模块内部按实际行为拆文件/函数即可；出现独立安装、依赖、授权或发布需求后再考虑拆 Module。首版不建设运行时 Mode/Policy/Engine 插件注册中心。

## 2. 通用实验对象与首版运营模型

### 2.1 最小对象与适用范围

| 适用范围 | 对象 | 最小事实 |
|---|---|---|
| 所有场景 | `TrafficScenario` | 有版本的网络/需求/服务资源引用、输入来源/有效日期、精度/模型说明、策略、时域与配置；不用另造同义 Scenario 类型 |
| 所有场景 | `ScenarioVariant` | 父场景版本、声明干预、目标对象、单位与派生输入；不原地改基线 |
| 所有场景 | `SimulationRun` | 场景/变体、持久归属、引擎/适配代码版本、种子/步长、实际配置、状态、终止原因、成果与帧索引 |
| 所有场景 | 结果/比较清单 | 原始输出、解析版本、指标适用范围/分母/窗口、共同条件、实验变量、异常和结果引用 |
| 启用乘客服务时 | `ServiceNode` | 上下客/换乘位置、泊位、候车容量、服务顺序和步行连接；疏散点/接驳点是首版角色，不强制所有节点有同一队列规则 |
| 启用乘客服务时 | `TravelerGroup` | 人数、到达时刻、起点、目的地、可接受方式、出行链、所在节点/车辆与服务事件 |
| 启用公共/预约服务时 | `TransportService` | 方式与具体模型版本、方向、线路/站序、班次或条件发车规则、容量、运行与换乘限制 |
| 启用车队服务时 | `FleetVehicle` | 车型/容量、实际位置或外部行程状态、任务、周转、下一次可用时刻；纯道路车辆不强制拥有车队任务 |

网络、需求、服务、资源和策略是区分输入与责任的概念，不要求各自成为类、服务或数据库。先对本期已实现配置做有类型的组合校验；不定义包含所有方式的巨大接口，也不用任意 JSON 参数袋代替领域约束。将来新增方式时允许显式扩展 Schema、校验器和视图详情，不承诺零核心改动。

启用旅客服务时，出行者或出行组的最小状态为：尚未到达 → 候车/步行换乘 → 乘车 → 接续候车 → 完成；取消、放弃和终止时未完成需分别记录。同一旅客在同一仿真时刻只能有一个状态和位置归属，不能同时出现在车上和候车队列中。

### 2.2 服务与资源守恒

- 每次上车同时检查旅客到位、车辆到位、可用容量、泊位及服务时段；车辆经过节点不等于服务完成。
- 公交班次占用实际车辆；包含驶往起点、上客、运行、下客、返回/转场与再次可用。新增发车计划不能凭空产生车辆。
- 网约车供给按实测或声明规则进入；完成订单后的占用与返回按实际范围处理，不无限注入空车。出租车与网约车需要分别建队列/规则时再增加独立车队。
- 点位候车容量满、泊位被占用或下游无法接收时，保留受阻状态与上游等待；不能静默删除或瞬移对象。
- 接续成功要求“实际到达 + 换乘耗时”满足后续班次上车条件，并有剩余运能；失败后按声明规则等待、改乘或计入滞留。
- 车道、节点、旅客、车辆、班次和外部行程之间维护稳定 ID 映射，显式核对插入失败、不可达和重复服务。

### 2.3 方式分配与调度

首版每个目的地方向维护少量合法候选出行链，比较人工给定的固定分担、按方向分流、预计等待时间分流、公交加班及网约车入场控制等规则。先验证规则效果，不以自动优化为前置条件。

区分“推荐方案”与“旅客实际选择”，对接受比例、步行容忍度、同行组和可接受换乘次数使用明确参数；无观测时标记假设并做敏感性试验。调度器使用当时可获得的信息，不能提前知道未来随机到达或真实延误；跨方式改乘记录原队列退出和新队列进入，不重生一份需求。

Python 协调层维护旅客、节点队列、资源约束和服务策略，SUMO 维护道路车辆动力学。上车/下车等状态只能有一处权威，适配时选定 SUMO 原生乘客接口或协调层账本的具体映射，不在两边各自扣减容量。P0 用守恒检查确定实现。

运行前冻结的是策略代码版本与参数，动作可以在 Run 内根据当时状态反馈执行。例如按候车人数/最长等待发车、按泊位占用控制入场；首版选一个可手算的阈值规则，与固定班表/固定放行基线比较。业务函数读取带仿真时间和状态版本的有界观测，产生类型化候选动作，由协调层校验并执行。正常的资源不足、无匹配或时窗已关闭记录等待/拒绝/保持原因，不默认中止 Run；非法策略输出、重复资源分配或引擎异常不能静默记成功，应按错误类别处理并保留诊断。

这种确定性规则反馈属于本期运营模型，不要求外部逐步控制接口。跨回合 Agent 调度、运行中更换策略、远程控制和任意策略代码上传仍在后续范围；不为首版抽象八类通用 Capability 接口或热插拔策略平台。

### 2.4 决策时钟与动作确认

P0 先写可检验的相位草案，再用同刻到达/发车与资源竞争样例修订；退出时冻结 P1 所需语义。计算步长、决策间隔与显示采样间隔分别记录，不能用浏览器刷新驱动决策。

| 边界 | 首版约定与待验证内容 |
|---|---|
| 初始时刻 | 初始化状态并处理 t0 到达后执行首轮决策；初始旅客/车辆与到达事件不能重复计入 |
| 观测截点 | 先推进至决策时刻 t，消化已发生事件，再生成快照；不含 t 之后的实际交通状态 |
| 同刻顺序 | 拟按运动/服务完成与资源释放、旅客到达/换乘完成、班次上客/关闭/发车规则分相处理；各类内使用声明优先级和稳定 ID。上客截止是否包含等号、上客耗时及发车条件由服务模型明确，并用同刻样例核对，不能由字典/线程/TraCI 返回顺序决定 |
| 冲突处理 | 候选动作以同一观测为基准，按固定优先级和稳定 ID 顺序校验并逐项预留资源，后续动作看到已有预留；不能让多个动作各自通过后占用同一辆车/泊位 |
| 动作生效 | 业务预留、提交引擎及效果确认分开；本轮动作不回溯改变观测，影响随后推进。需要引擎执行的动作只有观察到对应事件才确认效果，失败/无法确认保留原因，不提前扣减已完成服务人数 |
| 记录与重放 | 记录候选、拒绝/接受、引擎应用结果及实际服务事件的时间/对象关联；提交发车命令不等于车辆实际离开上客点。历史播放读取记录，不重新执行策略 |

采用上述确定性顺序即可，不引入通用事务或动作调度系统。资源暂不可用与程序/协议错误区分；若无法确认动作效果，不能将计划服务当作实际完成。未确认 Run 的处理仍沿第 5 节的执行与提交语义。

## 3. 总体架构与模块边界

```text
用户 / Geo 选区 / 已有路网、班表和需求
                 ↓
Pi：唯一 Agent Runtime + 仿真 Skill / 领域工具
                 ↓
薄 Pi Extension → 平台批准的交通服务
                 ↓
Node Host：归属、输入核验、作业、取消、结果/帧资源与发布
                 ↓
受管 Python 作业：旅客、队列、班次、调度、接续与指标
                 ↕ TraCI
无头 SUMO：道路车辆、公交运行及原始交通输出
                 ↓
服务事件 / 指标 / 帧与时间索引 / Run manifest
  ├─ Simulation Canvas：运行中观察、回放、时刻查询与方案比较
  ├─ Geo：输入选区、静态指标与空间分析
  └─ Document / Citation：报告与可核验依据
```

### 3.1 职责与交付

| 层 | 职责 |
|---|---|
| Pi / Skill / Extension | 理解问题、准备方案、调用工具、返回有界摘要和资源引用；不引入第二套 Agent Loop |
| Node Host | 当前计划/归属/授权、输入校验、受管作业、结果与动态资源、执行确认；不动态加载安装包的任意 Host 服务 |
| Python 协调层 | 确定性业务规则与统一时钟；只接收结构化配置，不接受模型传入任意 Python/SQL/XML 执行代码 |
| SUMO | 道路微观运行；通过受管 TraCI 调用同步车辆和服务状态 |
| Canvas Shell | 标签、视图身份、呈现生命周期和资源引用 |
| Simulation Canvas | Run、播放时间、帧状态、动态地图、节点/线路详情与仿真上下文 |
| Geo | 普通 GIS 场景、选区和静态成果；原 scene/revision、选区、截图与恢复语义保持 |
| Document / Citation | 对比报告与证据登记；呈现或引用失败不回滚已提交 Run |

场景准备、运营模型、运行执行、决策规则、实验分析和可视化是职责划分，分别落入上述已有层次；不是六个独立子系统、进程、工作台或新增安装单元。

交付拆为通用仿真能力模块与虹桥场景数据 Module。能力包提供 Skill、Extension、业务脚本和平台专属运行时；场景包提供有版本的数据与参数，依赖仿真能力。大型实测数据、原始视频和受限资产不进入源码仓库或基础安装包。

沿用 `manifestVersion: 2`、`type: module` 与 `com.transportx.traffic-simulation`，不为目录分类另造清单类型。依赖 Canvas、Geo、Citation、Document，分别用于专属呈现、GIS 输入/静态成果、依据与报告；依赖只影响装配，不传播工具 active。按现有工具按需启用机制开放工具。

### 3.2 平台接入增量

复用现有 Module Installer/Trust、Session Plan、`CORE_TOOL_BINDINGS`、TypeBox 同源契约生成、薄 Host Client、作业和能力中心投影。新增交通工具的批准契约、Host 路由/服务授权、领域结果解析、动态资源读取与 Simulation Adapter；不重新建设 Registry、诊断框架或通用插件 SDK。

工作区文件与成果属于 workspace；历史、冻结计划和呈现授权按 conversation 核验，live Pi ID 仅表示当前运行实例。查询/取消/读取帧均检查当前归属与计划；不能凭相同 cwd、runId 或复制的历史取得另一会话的高级资源权限。具体读写路径与当前 Workspace Host、租约及共享 `executionOwner` helper 对齐，不照搬旧稿的活动 Session 假设。

生产源码拟放 `modules/optional/traffic-simulation/`，通过有限静态映射接入构建、批准契约和独立输出；需同步排除基础安装包中的可选业务脚本/运行时。受信任 Renderer 随平台交付，模块 manifest 只声明所用 Canvas View，安装 ZIP 不提供动态前端代码加载权。

### 3.3 引擎边界与计算独立性

TransportX 的节点、线路、旅客、车辆、Run 与 Canvas 选择使用稳定业务 ID；SUMO edge/lane/vehicle 等 ID 保存在显式映射中，记录网络版本与一对多关系。查询可保留带引擎命名空间的原始 ID 以便诊断，但不能让通用工具、历史选择和指标仅靠引擎 ID 关联。没有语义对应时报告不支持，不强行制造统一对象。

将 SUMO 启动、步进、状态读取、动作应用、坐标/对象映射与输出解析集中在有限适配代码中，运营规则不散布 TraCI 调用。首版只实现这一条路径；不建设抽象引擎基类、Provider Registry、多后端回退或运行时切换。每 Run 声明实际支持的方式、运营行为与精度，准备阶段拒绝未支持的组合；引擎支持车型不能直接当作产品支持该服务。

冻结的场景与策略可由同一个确定性计算入口执行，不要求 LLM 每步参与，也不依赖 Canvas 打开。自动化验收/研究脚本可调用该入口；产品内的 Agent、UI 和后续批量入口共用 Host 的归属、预算与作业语义。首版不因此新增公共 API、外部 SDK、独立调度服务或绕过授权的执行入口。

通用 Run 生命周期、提交与结果索引不导入虹桥运营代码，不强制读取旅客/班次字段；模型通过类型化、版本化的事件/指标输出接入。组装当前作业的入口可以选择运营模型，但运营模型不能反向依赖 Pi、Canvas 或产品状态 store。

### 3.4 内部计算作业契约

Host 先完成授权、资源解析与预算核验，再生成版本化 Simulation Job Manifest 交给 Python。它是本次作业的显式输入清单，不是新的资源注册服务或权限事实来源；字段分为业务输入与受信任执行参数：

| 内容 | 来源与边界 |
|---|---|
| 业务输入 | 已冻结的网络/需求/适用服务、模型/策略版本与参数、时域/种子/单位/时区；由场景派生，仍需语义校验 |
| 已解析输入 | Host 核验过的文件位置、版本/哈希和对象映射；计算端不自行查找 Pi 会话或猜测工作区目录 |
| 执行参数 | 输出根、运行时/程序选择、墙钟/资源预算与必要环境由 Host 决定并与实际启动一致；业务 JSON 不能覆盖程序、路径根或抬高预算，用户请求的规模须落在批准预算内 |
| 输出约定 | 结果/事件/时间块的协议版本、位置、单位、覆盖范围与终止原因；Host 复核产物后提交 Run，不能照单接受计算端 success |
| 取消约定 | Host 沿既有 Job/signal 控制受管进程树并确认退出；不在 JSON 内传 AbortSignal、Host token 或任意取消脚本，不因写入取消标记就宣称已停止 |

计算作业允许依赖显式传入的文件、运行时和输出位置；不能读取 Pi Session、调用 Canvas/Host WebSocket，或依赖平台私有目录布局。产品归属和授权保留在 Host，计算输出只带必要关联标识，不获取产品凭据。Manifest 与必要输入副本记录实际执行版本/哈希，字段草案在 P0 实跑期间可调整，不在验证前承诺稳定公共 API。

## 4. 呈现架构决策：专属 Simulation Canvas，复用地图代码

### 4.1 选择与依据

**选择平台内置的 Simulation Canvas Adapter/Renderer；不复制 Geo 模块，也不把 Run、播放和帧生命周期塞入普通 Geo。** 这是对旧稿“不新增仿真 Canvas”决定的替换。

Simulation Canvas 是交通仿真模块声明使用的平台视图，不另建一个需要单独安装的“仿真画布模块”。新 Adapter 的前端实现随平台发布，是否装配/允许打开由当前计划与成果授权决定。

| 方案 | 收益与代价 | 决定 |
|---|---|---|
| 在 GeoWorkspace 内加入仿真业务 | 初期入口少；普通 scene revision/选区/截图会与 Run、时钟、回放相互耦合 | 不采用 |
| 复制 Geo 为一套仿真地图 | 可独立开发，但地图、图层、图例和修复分叉，长期维护两份 | 不采用 |
| 专属 Simulation 视图 + 共享地图渲染能力 | 增加受信任 Adapter 接入；Run/播放状态独立，共用地图实现 | 采用 |

当前 [Geo 契约](../src/contracts/geo.ts) 的每个 revision 携带完整 Scene；[GeoWorkspace](../src/web/features/geo/GeoWorkspace.tsx) 的选区、截图与上下文绑定该 revision。[Geo runtime](../src/public/visualization/geo/geo-runtime-entry.ts) 的内容 reconcile 会移除/重加图层，并使已有草稿失效。它们不能直接作为高频仿真帧协议。

当前 [Canvas Registry](../src/web/platform/canvas/adapter-registry.ts) 已支持按领域扩展受信任 Adapter，但尚无 Simulation。需补领域 payload/target/context 校验、CanvasView 投影、Renderer 懒加载、Host 资源校验及手动打开/Agent 呈现入口；manifest 声明不能替代这些实现。

### 4.2 复用边界

```text
Canvas Shell
  ├─ GeoCanvasRenderer → GeoWorkspace：普通 GIS 场景、输入与静态成果
  └─ SimulationCanvasRenderer → SimulationWorkspace：Run、时间轴、动态结果
                  ↓                         ↓
      共享地图能力：MapLibre 挂载/相机、图层编译、图例、样式与基础拾取
```

从现有代码按实际调用提取有限共享接口，不整份 copy，也不先写通用地图框架。第一版只抽出两种视图实际需要的挂载、图层/数据源、相机和基础拾取；共享图例/截图按接口成熟度复用。Geo 的请求应答、草稿附加和会话 stores 留在 Geo；Simulation 的时钟、订阅、对象详情和上下文留在 Simulation。共享渲染层不认识 runId、班次或旅客。

各 Canvas 实例拥有自己的 map、相机和选择状态，共用实现而非共享一个全局 Map 实例。不让前端仿真 Renderer 依赖 GeoWorkspace 的业务 store；共享资源读取经 Host 授权解析，不能把仿真资源伪装成已发布 geo_* 资源。

Simulation Canvas 用稳定 viewId 绑定 Run；Canvas revision 只反映呈现/资源版本，动态 frameSequence 不增加 Canvas/Geo revision，不逐帧写 Pi 消息历史。指标快照、线路和对比结果可按需通过 `publish_geodata → present_visualization` 发布到普通 Geo，资源仍按其原规则核验。

### 4.3 通用呈现结构与首版交互

Simulation Canvas 消费网络几何、交通实体位置/状态、服务、运行指标、领域事件与实验时间轴。这里只约定已实现数据的呈现结构，不预建全部方式的图层、详情和事件插件。运营代码输出状态与事件，Renderer 不执行匹配、排班或借还算法；出生/移除/位置等基础动画复用，方式专属详情用受信任的类型化分支按需增加。

| 内容 | 表达 |
|---|---|
| 疏散点/接驳点 | 分方向队列、等待时间、泊位占用、下游接收状态 |
| 公交/网约车 | 按实际轨迹定位、方向、任务和载客状态 |
| 线路与地铁服务 | 路线、班次、运输量、满载与接续状态；无列车轨迹时只显示班次信息 |
| 道路 | 速度、排队和回溢，对服务造成的延误 |
| 事件 | 上下客、匹配、发车、接续失败和策略动作；按时间与对象查询，不为每条事件创建地图标记 |
| 时间轴/详情 | 计算进度、观看时刻、播放速度、所选对象指标与事件 |

上述节点/线路详情是首版服务模型的视图；纯道路场景只显示实际存在的网络、车辆与指标，不要求空队列或伪造服务数据。没有实现借还/库存模型时，不显示共享单车可用性；不能通过地图图标宣称仿真能力已经支持。

点击节点/车辆/线路时使用稳定对象 ID 查询同一 Run、同一仿真时刻。附加给 Agent 的上下文冻结 runId、场景版本、时间/帧与对象引用，由 Host 核验；不能仅传“当前地图”或随着播放漂移的选择。请求修改方案时创建新变体/Run，保留原结果。

遵循工作台 semantic token、主题与字号约束；普通 Geo、Simulation 和报告使用一致的指标名称、单位与图例，不把未标定阈值画成已证实风险等级。

运行摘要、输入详情与导出结果明确标注“仿真结果”、输入来源/有效日期（实测、运营计划、假设、合成）及模型校准/验证状态。实测输入产生的轨迹仍是模拟输出；来源不等于置信度，混合来源分别记录，不生成无统计依据的置信分数。首版不强制将所有含假设输入的车辆画成虚线或半透明，保留清楚的业务图例与运行级标识即可。

## 5. Run 执行、运行中可观察与增量回放

### 5.1 有限 Run 与状态确认

首版运行完整、有预算的无头 Run，内部通过 TraCI 推进；“实时观看”在产品中指运行中可观察与增量回放，不承诺仿真时间、墙钟和显示完全同步，也不需要跨模型回合保持 start/step/control Worker。拟采用 `prepared → running → finalizing → ended`，无法确认执行/提交时保留 unknown；结束原因、清理状态和已发布数据范围分别记录。

执行先核验归属和输入，持久记录 operationId、Run ID 与 toolCallId，再派发既有受管 Job。SUMO 结束后核对最终时刻、服务/车辆数量、原始输出、指标、帧索引和哈希，以结果 manifest 提交确认成功；进程退出 0、已有轨迹或 UI 可播放都不等于成功提交。

沿用当前有界等待的 runJob，不用提前结束 HTTP 响应制造后台运行语义。订阅可以与运行请求并行读取进度；关闭/隐藏 Canvas 只停止观看，不取消作业。用户请求取消计算时，沿 Pi signal、Job、Python/SUMO 进程树核验退出；工作区租约在作业与进程状态确认前不能释放。

Host 重启后核验已提交成果；不能确认时保持 unknown，不按旧 PID、缺失内存 Job 或响应丢失自动重跑。结果查询、呈现失败和 Citation 登记失败只重读/重试相应步骤。同一操作同一输入复用确认，输入冲突拒绝；新 ID 不绕过未确认 Run 的核对。

### 5.2 统一时钟与完整时间块

仿真时间、墙钟时间和观看时间分开。跨午夜按服务日期、时区和单调仿真秒保存，不能把次日 00:10 排在当日 23:50 前。协调层、SUMO、地铁班次与外部行程使用同一时间基准和明确事件顺序；步长及舍入规则纳入 Run。

首版采用可独立恢复的完整时间块：每块包含 Run/场景/协议身份、时间范围和序号、可恢复的块起始状态、块内采样记录，以及对应事件范围/引用；从任意块开始播放不依赖上一块的内存状态。块边界包含规则与事件序号范围须明确，起始快照只作恢复点，不重复计入分析事件。静态路网/样式通过固定版本引用复用，不在每块复制；“完整”表示恢复所需数据齐全，不要求每个计算步完整复制全部车辆、节点及历史事件。

用于守恒、指标和服务回查的必要业务事件/分析数据完整记录；展示轨迹允许采样，记录频率与缺口。出生/移除、上下客和动作应用用类型化、版本化事件表达，事件只保存一次，播放块可以引用相应事件范围。节点人数、车辆载客和线路指标对应同一已发布时刻；位置插值只用于显示，不产生服务事件、不让车辆穿越道路转角。

当前 PythonRunner/ProcessRunner 在结束后返回有界 stdout/stderr，尚无运行中数据消费接口。首版拟由 Python 写块文件，完成并核对后原子发布带时间范围、大小与哈希的索引；已发布块不原地修改，Host 只读取完整块。未发布尾块不可见，故障前已发布块标为部分结果，最终 Run manifest 决定结果是否提交。终止时在可能范围内封存完整尾块并注明覆盖终点；缺口不能补成零。P0 实测格式、块时长、内存/磁盘、读写与可见延迟，不把全场数据放内存或 stdout。

Host 通过既有 WebSocket/Kernel 通道通知索引版本/进度，Canvas 经授权读取按时间定位的块；写命令继续走可靠 RPC/HTTP。断线或通知缺失后重新读取索引并定位完整块，切换 Run/会话后拒绝迟到响应；通知合并且队列有界，慢消费者可跳过动画但不丢分析事件。首版不依赖跨块增量链，不先建设复杂关键帧/差分压缩协议，压缩与索引优化按实测需要增加。

### 5.3 播放与资源语义

- 展示 latestComputedTime、availableFrameTime 和 playbackTime；计算可以领先于可见帧，观看也可以停在历史时刻。
- “暂停观看”不暂停计算。拖动仅进入已有帧的范围；无数据区间显示缺失，不外推未来状态。
- 隐藏标签暂停绘制与数据订阅，重新显示从最新索引定位完整块；不因标签关闭、切换或重连重新启动 SUMO。
- 原始事件与指标支持分析，位置帧可按声明频率采样；记录采样率和覆盖范围，不声称显示了每个计算步。
- 计算可以领先显示，但可见延迟仍需记录并设验收范围；块发布/通知频率、采样率和播放速度分别配置。先测代表场景，再确定 P1/P2 的可用规模与预算，不预填固定推送帧率。
- 截图/导出冻结 Run 与观看时刻，等待该帧绘制后生成，并保留基图/帧版本与单位。实时部分成果不得作为已完成实验的正常收益证据。
- 已提交结果通过持久 conversation 与资源授权读取，无需启动 Pi。输入变化创建新场景版本，历史 Run 不跟随最新场景漂移。

### 5.4 性能验证口径

基线同时记录硬件、运行时版本、路网、步长、决策/查询频率、采样率，以及累计人数/车数和峰值活跃人数/车数。分别测 SUMO 推进、TraCI 读取/路径查询、Python 规则、序列化/落盘、Host 读取与浏览器绘制；不能仅以车辆数量推断瓶颈。

验收分开记录仿真推进速度（仿真时长/墙钟耗时）、数据从对应仿真状态产生到可见的延迟、播放帧率、内存/磁盘占用与结果完整性。P0 先测计算/输出/块读取的小型与代表规模基线，冻结 P1 所需最小预算；P1/P2 补 Host 到 Canvas 的可见延迟、播放表现与目标场景验收。无“5000 辆车/10000 人”等未经需求和硬件支持的硬门槛。

若超出目标预算，先定位瓶颈，再评估减少重复查询、订阅/批量读取、显示采样或 libsumo。不得静默减少必要服务事件、人数或改计算精度以伪造性能达标；改变研究假设需另建变体并记录。

## 6. 数据准备、指标与校准

### 6.1 最小数据与空间映射

| 输入 | 必需内容 |
|---|---|
| 到达需求 | 疏散点、分时/批次人数、目的地方向、出行组；初始已候车/已乘车人数明确 |
| 节点 | 位置、方向、泊位、容量、服务顺序、步行/换乘连接和进出规则 |
| 路网 | 几何、车道、连接/转向、信号、权限、限行、背景交通及外部行程边界 |
| 公共交通 | 线路/站序、日期/时刻表、车辆/班次容量、剩余运能、条件发车和夜间停运规则 |
| 车辆供给 | 数量、类型、初始位置、排班/任务、调入/返回/转场时间 |
| 标定数据 | 到达、发车、载客、运行时间、排队/等待与网约车周转观测 |

路网可以来自已有 SUMO 场景、授权 GIS/OSM；班表可导入 GTFS 或统一结构化文件，不把存在完整虹桥开放 GTFS 当成前提。在线 OSM 获取在固定样例闭环后接入；自动生成的连接、车道和信号须核验，不能将推测值标为实测。

网络、需求与服务/资源配置分开记录版本或内容哈希，由场景引用；未启用服务模型时不强制提供班表和乘客输入。首版使用现有授权 Data 资产或工作区内冻结文件即可，不新增 NetworkAsset/DemandAsset/ServiceAsset 注册服务或 ModuleAsset kind。引用要绑定实际版本和内容，Run 保留必要副本或可长期核验的授权引用，不能引用会漂移的 latest 路径。

仅修改班次、车队或需求时复用已验证网络，不重新取数/转网；车道、拓扑、权限等影响建网的输入变化则生成新网络及映射。复用键至少覆盖源内容、转换工具版本、选项与映射版本，命中后仍检查授权与完整性；不为复用先建全局缓存/数据仓库。

建立 GIS ID ↔ SUMO edge/lane ↔ 节点/线路映射。记录源 CRS、单位、投影、偏移与转换版本；SUMO 本地米制坐标转换为 WGS84 显示，地图底图/其他数据的坐标来源单独核对，不按视觉偏移硬对齐。仿真路线沿合法道路展开，不用疏散点间直线代替实际路径。

虹桥场景按有效日期冻结上客区、接驳点、班表和组织规则。公开资料用于识别对象和规则，不替代精确需求、路网、容量及运行参数的授权数据。缺失项以“假设/待核验”登记，不自动填成确定事实。

数据准备从 P0 与技术验证并行：列出最小数据集、来源/权限、有效日期和缺失项，区分可用于开发的合成输入与 P3 所需观测。技术样例可以使用已标注合成需求，但不得据此推断真实虹桥收益；真实数据等待不阻塞固定样例，取得数据前不宣称完成校准。

### 6.2 指标与可比性

按启用的模型声明指标及适用范围。道路场景输出运行时间、速度、排队、发出/完成/未完成车辆与异常；首版疏散再输出各点/方向/方式候车人数、平均及 P90 等待、累计服务与完成出行人数、离开枢纽和完成出行链耗时、错过接续班次/末班人数、车辆利用率与周转、外部行程与滞留。未启用模型的指标标为不适用，不填零；单位、分母和窗口保持可查询。

人数、组数、车次与车辆数分开；记录指标窗口、单位、分母与截尾。旅客守恒按已到达需求核对候车、步行、乘车、完成及明确终止/放弃等互斥状态，尚未到达的人数单列。仿真结束时仍在车上或外部行程中的旅客不是已完成；未完成旅客不能从等待统计中无声消失。

比较固定外生到达需求、目的地需求、初始状态、背景交通、时域与相应随机条件；允许变化的车队、班表、路径、分流/服从参数或入场控制逐项声明。新增运力同时报告资源成本，不要求所有输入哈希或路径相同，也不因都叫 baseline/policy 就认定可比。

需求/行为/交通使用分离随机流，采用配对种子及多种子实验，避免策略改变随机调用顺序后连外生需求也改变。缺失不是零、基线为零不计算普通变化百分比。执行中止/unknown 的结果只用于诊断，不生成正常收益结论。

### 6.3 真实场景验证

软件验收与交通模型验收分开。先复现一组历史夜间的分时队列、发车/载客和运行时间，再使用独立日期检验；参数标定集与验证集分开。验收误差范围由数据质量与用途确定，实施前记录，不预填无依据的准确率。

对客流峰值、目的地分布、方式接受比例、上客耗时、道路时间和车辆供给做敏感性分析。数据不足时交付带假设的试验模型和参数区间，不能宣称已证明虹桥实际改善。观测缺口、获取权限和采集工作独立列入实施依赖。

### 6.4 轻量实验设计与执行记录

在现有比较清单中记录实验设计：基线/变体、配对种子、参数取值、指标定义与预期 Run 引用；完成后关联各 Run 的真实状态和结果。清单用于组织与复现，不另建与 Run 竞争的进程状态机、全局实验数据库或 Experiment Lab 服务。

P2 支持少量方案与多种子的有界顺序执行及汇总，计划展开前校验总 Run 数、总时域和资源预算。失败/取消/unknown 明确列出，不静默丢弃或自动补跑；按相同种子成对比较，并展示样本数、差值分布与未完成样本。一个种子仍只用于功能闭环，不能作为效果证明。

参数敏感性以少量明确取值形成变体，记录单因素或多因素设计，避免把关联变化误认为单因素收益；不默认展开任意参数的笛卡尔积。候选方案生成、校准算法和大规模批量调度后置，产生的候选仍进入同一变体/Run/比较链。新入口需要时再增加，不为每种方式复制实验工具。

| [JuPedSim](https://www.jupedsim.org/stable/) | 室内/二维人群问题的后续候选，本期范围不需要 |

SUMO 的 [多方式路由](https://sumo.dlr.de/docs/IntermodalRouting.html) 不能直接当成考虑容量和排队的全局分配器；其公共交通文档说明运行中新增停站不会自动纳入原生 personTrip 路由。动态班次/服务变化由协调层显式维护候选出行链与可行性，不假设引擎自动完成。

旧稿对 AgentSUMO 的固定源码核查仍有参考价值：独立包/主项目 Python 要求不同；Runner 单次调用内部循环 TraCI、整场积累轨迹；结果导入含按路网/命名去重逻辑；路径/默认解释器、忽略路由错误、超时结束与成功状态需要适配。它们是适配风险线索，不是本轮实跑故障。P0 比较“直接 TraCI + 少量局部复用”和“有限修改 AgentSUMO 执行层”的实际成本，最终只交付一条路线。

MCP 不是首版前提。只有所选执行函数确需私有 stdio 时才保留；每作业独占后端、回收进程树、stderr 与协议 stdout 分流，第三方后端不接收 Host token/模型 Key。避免为了几项函数引入整套服务和依赖。

TraCI 是本期默认控制路径。官方建议无 GUI 且性能受限时评估 libsumo，但实际收益、进程隔离和 Python/原生打包仍需测量；P0 先记录基准，只有确有瓶颈再立项替换，不同时维护两套后端，也不把相似 API 当成无需验证的等价语义。

### 7.2 原生运行时与资源预算

当前 Native Runtime 契约只支持 ffmpeg/ffprobe；SUMO 需要扩展契约、安装/兼容性、解析、计划冻结和恢复校验。发布能力包携带无头 sumo/netconvert/duarouter、必要工具/typemap 与经验证的 Python 依赖，OR-Tools 后续按需加入。开发可显式覆盖路径，发布不依赖系统 Python、Conda、Homebrew 或运行时自动 pip。

锁定实际引擎/依赖/脚本内容与哈希，保留复用来源和许可证；按平台检查动态库、重定位、签名/许可及无符号链接安装约束。文档或 PyPI 声明支持 Python 3.10 不等于整链双平台已通过。OS/架构/入口与发布事实继续集中在 platform-profile.mjs。

P0 排查 macOS arm64 / Windows x64 的程序来源、依赖/许可与最小运行目录，使用干净临时目录并搬移后验证启动、有限执行、取消及退出，不要求此时完成 Electron 安装器或签名流水线。CI 可承载相同检查，但不是开始验证的前提；未取得目标机证据的项目保留待验，不视为该平台已通过。平台无关工作可继续，目标平台支持与正式安装/签名/升级承诺仍以 P4 证据为准；无法分发的根本依赖风险需先处理，不能只后移记录。

ProcessRunner 当前合并父环境；需补显式环境替换并贯穿 PythonRunner，其他调用保留默认行为。验证 Host 凭据和父进程测试标记不进入嵌套 SUMO/Python/MCP。对 XML 间接引用、输入/输出真实路径、资产授权根和符号链接核验；设置 cwd 不等于文件隔离，也不宣称 OS 沙箱。

每工作区首版最多一个活动 Run，同时遵守现有 Job/进程与工作区门禁；统计嵌套进程及轨迹体量，不只计算最外层 Python。研究范围、人数/车数、时域、墙钟、下载、内存、磁盘及单次读取预算用固定/代表场景实测后冻结。

## 8. 工具、存储与平台接入位置

### 8.1 工具面

候选工具名仍为设计，未形成已发布兼容承诺：

保持场景、变体、Run、查询与比较这一组工具，以有类型的输入区分已实现服务。场景准备可以先返回缺失项，再从相同冻结输入执行，不为每个小步骤或交通方式新增同义工具；独立的需求编辑、网络检查、策略应用或实验批量工具仅在真实调用需要时增加。

| 工具 | 首版操作 |
|---|---|
| traffic_prepare_scenario | 按所选模型检查来源、支持范围与缺失项，复用/构建并冻结网络、需求和适用的服务/资源/策略 |
| traffic_create_variant | 按批准的干预类型修改本期支持的道路或服务参数，创建独立变体；拓扑变更仍需单独建网/映射验证，接口不开放任意编辑 |
| traffic_run | 持久受理关联后执行有限 Run，发布专属视图引用并返回最终确认 |
| traffic_execution | 查询阶段/进度/提交事实，或请求取消；取消不是另一个 Run |
| traffic_query_results | 按 Run、时刻/时间窗、对象与指标有界查询 |
| traffic_compare_runs | 核验共同条件与干预，生成比较、静态 Geo 图层及 Document 报告 |

视图应在开始运行时可被用户打开，不能等 traffic_run 最终 tool_result 才出现。P1 由 Host 在持久受理后发布 Run 引用事件，工作台以受信任 Adapter 投影并打开 Canvas；刷新时从授权 Run 记录重建可打开入口。最终工具结果沿 Pi 历史保存同一视图/成果引用，历史不存帧。提前呈现的事件投影与读取入口属于本期新增工作；呈现与执行/最终提交分别确认，不将内存进度冒充已提交成果，也不把每帧当成新的工具调用。

运行中的对象查询只读已发布帧/事件索引，返回覆盖时刻及“运行中/部分结果”标识；已完成结果查询读取提交后的指标与数据库。不得读取正在写入的尾块或未提交数据库，并将其当作完整指标。

工具输入在平台 TypeBox 权威中定义，沿 CORE_TOOL_BINDINGS 同源生成包内/Host 批准契约；包内描述不能授予 Host 权限。薄 Extension 只传已批准操作，signal/toolCallId/当前计划由可信链提供。只读查询沿有界读取；昂贵构建/Run 使用持久确认与既有作业；取消沿原执行记录，不为所有操作强制新建 Job。

模型工具契约与内部 Job Manifest 分开版本化，Host 负责授权、字段来源和显式转换，Python 校验实际计算输入并返回版本化输出；二者不机械共用同一 Schema。P0 用一组共享的有效/无效样例核对工具输入→作业清单→结果/错误→Host 状态：覆盖时区/跨午夜、单位、ID 映射、时域/种子、缺失/错误字段、越权覆盖执行参数，以及取消/部分结果。合法类型归一化和单位转换须明确，不依赖隐式强转；不为此预选 Pydantic 或自动生成全部跨语言类型。

能力中心沿 platform.getOverview() 核对当前计划、精确来源、active、Schema 与已确认领域结果，区分准备成功与 Run 成功；沿原错误投影增加交通协议，不重建状态表。模块信任/安装仍走原生入口。

### 8.2 成果存储

```text
<workspace>/traffic-simulation/
  scenarios/<id>/     scenario.json、冻结的网络/需求/适用服务输入或版本引用、mapping
  variants/<id>/      intervention.json、派生输入与校验
  runs/<id>/          run.json、实际配置、原始输出、results.sqlite、metrics
                      frames/、events/、分块索引与已提交结果 manifest
  comparisons/<id>/   comparison.json（实验设计与 Run 引用）、静态 GeoJSON、报告
```

文件位于工作区，执行确认在用户数据根 executions/traffic-simulation 下按持久归属保存；当前 conversation 的高级资源发布与 Run 对应关系由 Host 核验。路径以 POSIX 相对路径序列化，输入/输出用真实路径与 SHA-256 校验；原始输入可来自计划授权的 Data 资产，不能从模型参数接受任意资产根。

每 Run 一份 results.sqlite，记录 schema/解析版本并暂存导入后核对提交；不按网名去重或覆盖其他 Run。首版参数化查询固定对象/指标/窗口，不开放任意 SQL。SQLite 是结果索引，不能成为会话、Job 或进程状态的第二权威。

## 9. 实施阶段与后续优化

本次重新定义 P0–P5；阶段编号不再沿用旧稿含义。首个可用版本完成 P0–P2，虹桥可信分析需 P3，桌面对外交付需 P4；P5 为后续增强。

| 阶段 | 交付 | 退出条件 |
|---|---|---|
| P0：技术与业务验证 | 纯道路与最小疏散真实执行；作业清单/转换、时间相位、状态权威、独立时间块、性能与运行时风险验证 | 按 9.1 节四项门槛提供运行证据；冻结 P1 需要的最小契约与预算，未验证平台/参数如实列出 |
| P1：独立模块与专属 Canvas | 真实 Pi→批准 Host→Python/SUMO；独立包、归属/取消/确认；Adapter 与共享地图最小提取，按 9.2 分批验收 | 模块移出源码树仍可执行；能看、能查、能恢复均通过；运行中可打开、普通 Geo 无回归、错误/unknown 可查询，不重复派发 |
| P2：多方式方案比较与回放 | 多点、多目的地、公交多趟/网约车/地铁接续；固定基线与一个阈值反馈规则；多种子实验清单；时间轴/详情/恢复/报告 | 线路与需求闭环；反馈只用当时观测且动作可回查；同刻指标一致；满载/错过班次/积压可复现；有界顺序 Run 可成对比较；暂停观看不暂停计算 |
| P3：虹桥场景与校准 | 有效日期明确的场景包、真实输入/规则、标定/验证日期与敏感性试验 | 对照观测核验需求、队列、发车、载客和运行时间；误差门槛与数据缺口有记录，才解释实际收益；在线输入按需接入 |
| P4：桌面分发 | 独立平台运行时、安装/恢复/卸载、版本/许可/签名与历史读取 | macOS arm64 / Windows x64 干净环境验收，不依赖开发机环境；实验性 Linux 支持单列，不推断已通过 |
| P5：自动优化/在线控制 | 按真实问题增加候选生成或滚动控制 | 优化结果通过同一变体、可行性和仿真比较；在线写命令与恢复单独验收，不因有实时地图就视为已支持 |

P0 使用固定本地输入，在线 OSM/实时数据、自动优化和跨回合 step 均不阻塞首条链路。地图共享提取以保持原 Geo 行为为验收条件，不借此重写相邻功能。虹桥是首个业务交付场景；共享单车、第二引擎或额外城市案例不作为 P3/P4 前置。数据盘点与平台风险验证从 P0 开始，完整 Agent 产品链路和成品分发分别在后续阶段验收。

### 9.1 P0：草案、实跑与退出证据

| 时点 | 产出 |
|---|---|
| 开始前 | 可执行/检验的 Job Manifest 草案、状态权威表、事件相位、两个固定样例及运行时来源；不要求冻结所有字段/步长/块格式/性能阈值 |
| 验证期间 | 实跑纯道路与最小疏散，验证取消/异常、同刻事件、跨层转换和块发布；依据记录修订草案并注明被推翻的假设 |
| 退出时 | 冻结 P1 依赖的最小作业输入输出/错误、时间与事件、结果提交和块读取语义及可用预算；明确版本、样例、运行证据和待验项，不形成永久公共 API 承诺 |

P0 的验证门槛为：

| 门槛 | 需要的实际证据 |
|---|---|
| 跑得起来 | 在受控环境真实启动 Python/SUMO，复用受管进程机制验证有限运行、取消/异常与退出；保存命令/配置/版本、终止原因、输出及性能分解，排查目标平台来源/依赖/许可/重定位 |

| 边界清晰 | 纯道路和最小疏散共用计算契约、Run/提交格式，通用层不强制疏散对象；转换样例验证可信字段来源、单位/时间/ID、错误与部分结果，网络复用和版本变化可核对 |

### 9.2 P1/P2：纵向产品验收

P1 的专属 Canvas 分三个内部里程碑，不新增阶段、独立服务或第二套地图：

1. **先能看**：指定 Run，读取已发布完整块，显示网络/车辆与时间轴；只提取当前确实共用的地图能力。
2. **再能查**：选择车辆/节点/线路，查询同一 Run、同一观看时刻的状态和事件，构造冻结上下文。
3. **再能恢复**：运行中打开、刷新/断线索引恢复、历史读取、跨 Run 切换与迟到响应隔离；保持普通 Geo 选区/截图/图例不变。

三项是实施顺序，不是降低 P1 完成标准。P1 验证自然语言任务中的工具发现、缺失项诊断、一场真实 Run 呈现与对象查询；P2 再验收完整任务：“使用当前地图选区和指定数据，建立基线与公交增班方案，执行两组实验，在仿真视图中查看并解释等待时间与道路拥堵的差异”。

验收需核对实际调用、冻结条件、Run 记录、选中对象上下文和指标引用；关键输入缺失时报告缺口，不擅自伪造已确认数据。固定模型响应只能证明工具链，真实模型自主任务另留证据；无有效结果时不得自行估计收益。不新增 Agent Runtime/Planner，也不承诺特定版本交付或未经验证的精度。

### 9.3 后续优化

后续优化目标围绕旅客等待、出行完成、末班接续、滞留与运力成本设置，明确目标优先级或权重。旧稿“单趟站点访问 VRP、最小车队总旅行时间”不能直接覆盖本问题；多趟车辆、班次接续、接驳点容量和网约车供给需明确建模。首版先比较人工规则，具备校准数据后再选 OR-Tools 等求解器。

求解器只产生候选：核对有解/最优证明/终止原因，超时无解不等于不可行；容量、时刻与实际服务验证通过后建立独立变体/Run。离线方案不覆盖运行中配置；滚动调度需额外记录决策时刻、可见信息和应用事件。

## 10. 验收与证据

文档检查不代替第三方运行验收；固定样例不代替真实场景标定；软件测试不代替模型有效性。后续实施先运行 npm run test:budget，再把必要断言并入既有关键场景，实际注册总数不超过 40；本轮只有文档更新，不运行全量构建。

验收按纵向场景组织：

1. **真实装配与复用**：安装/信任/选择→Pi 契约→Host→无头 SUMO→Simulation Canvas→查询与报告；同一计算入口可无 LLM/地图执行纯道路样例，不强制旅客服务字段；跨语言转换拒绝覆盖可信执行参数，输出/错误语义可核验；仅改班表复用网络，版本变化生成新映射；未装配/未授权、不支持的组合和越界在派发前拒绝。
2. **业务守恒**：用可手算样例核对逐组人数、车辆/班次、泊位、满载、周转、跨午夜与末班接续，以及 t0/同刻顺序/动作冲突；资源不足可等待，命令接受不冒充实际服务，不重复服务或凭空增车。
3. **干预与实验**：共同需求保持，车队/班表/路径/分流变化均可追踪；阈值规则只读取已发生观测，记录动作时刻和状态；小型配对多种子清单逐一关联 Run，失败/unknown 不被忽略；输入不可比或 Run 未确认时拒绝正常收益结论。
4. **运行中可观察**：计算结束前打开专属视图；完整块独立可读、未发布尾块不可见，采样/必要事件分开；指标同刻、拖动范围有界；按索引断线恢复、拒绝迟到数据，隐藏标签不取消计算，不逐帧写消息历史；分别记录推进速度、可见延迟、帧率与资源占用。
5. **Geo 隔离与复用**：普通 Geo 同时打开仍可选区、附加上下文、截图与控制图例；Simulation 帧不清空其草稿，不改变其 revision；共享地图修复只维护一份代码。
6. **执行恢复**：同操作不重复、输入冲突拒绝；提交后丢响应重读原成果；取消请求/确认退出/unknown 分开；Host 重启不自动补跑，租约与进程回收可核验。
7. **成果读取**：历史回放无需启动 Pi；不同 Run/会话的资源和帧不串用；部分帧与最终提交状态分开；报告引用失败不触发重算。
8. **模型与分发**：输入来源与校准/验证状态在视图及导出中一致，仿真输出不冒充观测，不打无依据的置信分数；独立日期与敏感性分析提供业务证据；各平台按阶段验证最小运行目录和最终安装/恢复/卸载及许可。

新增运营模型时使用一张核查清单即可：所需网络/需求/服务输入；SUMO/Python 的唯一状态权威；时钟与类型化事件；资源守恒；状态/指标适用性；通用显示与专属详情；最小验证案例。清单落入对应模型说明与验收，不对应七个类、注册器或新子系统。

### 评审意见取舍

| 建议 | 本次决定与原因 |
|---|---|
| 通用仿真底座与场景扩展分开 | 吸收：通用生命周期/输入/结果与可选运营模型分开；不把所有业务抽象为十个统一类 |
| 网络、需求、服务资产独立 | 吸收版本引用与重用；本期沿用文件/既有 Data 资产，不建三个资产子系统 |
| 稳定业务 ID、有限引擎适配、计算独立于 Agent | 吸收；不附带多引擎框架、公开 SDK 或第二套运行服务 |
| 六个核心子系统、组合式能力接口 | 作为职责检查参考；尚无第二实现需求，不建设六套产品界面、Capability Registry 或策略插件加载器 |
| 提前增加闭环控制 | 部分吸收：本期明确决策相位、资源冲突和动作效果确认，采用确定性阈值反馈；外部 Agent 写命令、热替换和逐步控制仍后置 |
| Experiment Lab 与优化器可插拔 | 吸收轻量实验清单/配对种子和函数边界；自动优化/大规模调度不成为首版门槛 |
| 通用 Simulation Canvas | 吸收状态/事件呈现结构，保留专属视图和地图代码复用；新方式的详情仍需实现与验收 |
| 首版扩展自行车/共享单车，虹桥移至后续 | 不采用：库存借还与再平衡增加独立业务；保留当前疏散交付，只增加小型纯道路复用检查 |
| Agent 提出下一轮建议，由用户决定干预 | 保留授权边界；已授权的批量实验可继续执行，不额外增加逐次审批，超出授权再询问 |
| P0 前冻结全部契约、性能门槛与流水线 | 不采用：先有草案，P0 实跑修订后冻结 P1 所需最小契约；性能基于代表规模测量，完整安装/签名仍在 P4 |
| 首版关键帧/跨块差分及数据置信度强样式 | 收敛为独立完整时间块与来源/验证状态标识，保留可见延迟验收；压缩按实测增加，不把来源等同数值置信度 |

这些取舍是本轮产品与架构判断，不把评审意见中描述的长期能力作为已经存在的支持承诺。后续新增模型应有可运行案例、输入要求、状态权威、指标适用性与验收证据。
