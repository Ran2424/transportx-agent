## 2. 场景范围与运营模型

### 2.1 使用场景

交通仿真模块 `com.transportx.traffic-simulation` 面向交通建模与方案评估。首版以枢纽夜间疏散为业务用例，处理公交与网约车并行分担，以及接驳公交到地铁等连续接续。典型流程是检查并冻结输入、声明方案变化、启动受管 Run、观看和查询同刻状态，再比较等待、全链完成、错过末班、节点积压及车辆周转。

固定样例从单疏散点、单接驳点和两个目的地方向起步，扩展到多个上客点、接续点和线路。纯道路场景共用计算与回放入口，乘客服务字段按模型启用。合成示例提供可重复输入，实际虹桥项目需准备有有效日期的运营数据并独立校准。

| 对象 | 首版建模精度 |
|---|---|
| 道路 | SUMO 逐车微观运行，考虑路网连接、车道权限、转向、信号、跟驰、换道和背景交通 |
| 公交与接驳车 | 有限车队、线路、班次、泊位、上下客、发车条件与多趟周转 |
| 网约车 | 按有限供给及服务规则匹配，记录候车、上客、离场与再次可用，车辆占用和旅客队列分别计量 |
| 地铁 | 有限班次与容量，核对接续时刻、剩余运能、末班关闭及外部行程 |
| 节点与旅客 | 逐人服务状态、候车容量、泊位和步行接续。铁路、航班等到达作为外生需求输入 |

道路微观范围根据线路与拥堵影响确定，远端行程可用有来源的分时旅行时间表达。离开微观路网和完成全链分别记账。共享单车、需求响应公交、精细轨道动力学和室内人群属于后续模型，按具体问题核验数据、状态权威、资源约束和成本。

### 2.2 场景、变体和对象

| 对象 | 记录内容 |
|---|---|
| 场景 | 有版本的网络、需求和可选服务资源、来源与有效日期、模型、策略、时域和配置 |
| 变体 | 父场景和声明的干预，记录目标对象、单位与派生输入。基线保留原版本 |
| Run | 场景或变体、归属、种子、步长、引擎与代码版本、实际配置、状态、终止原因、成果与时间块索引 |
| 比较清单 | 共同条件、干预、配对种子、各 Run 的真实状态与结果引用、指标口径和异常 |
| 运营对象 | 节点、旅客或出行组、运输服务和车队车辆。各自记录适用规则、容量、任务、位置与事件 |

业务对象使用稳定 ID。保留 GIS 对象、SUMO edge/lane/vehicle、节点与线路的显式映射，以网络版本约束查询与复现。每个模型声明支持的输入组合，缺失或不支持的语义在准备阶段报告。

### 2.3 守恒、时钟与调度

SUMO 提供道路运动、停靠、离站和返场观测。Python 运营账本负责旅客状态、节点队列、容量和班次。同一旅客在一个时刻只有一个状态和位置归属，尚未到达、候车、步行、乘车、接续、完成和未完成分别记录。上车检查人车到位、剩余容量、泊位和服务窗口。满载与下游阻塞保留等待，车辆确认实际返场后恢复可用。接续以实际到达加换乘耗时计算，再核对班次和运能。

仿真时钟按服务日期、时区和单调仿真秒记录，支持跨午夜。决策相位依次处理运动与服务完成、资源释放、旅客到达与换乘完成、班次匹配与资源预留、引擎提交及快照。同刻候选按规则和稳定 ID 解决冲突。命令接受和后续观测到的实际效果分别记录，重放读取记录中的结果。

固定班表与公交队列阈值反馈已验收。反馈只读取决策时刻已发生的观测，记录候选、拒绝、预留、提交及效果。后续分流、改乘和入场控制可沿同一链路评估，明确接受比例、等待、步行及换乘假设，保持需求守恒。

## 3. 系统架构与 Run 生命周期

### 3.1 计算链与模块边界

```text
Geo 选区与授权输入 → Pi Skill / Extension → Node Host 受管 Job
                                              ↓
                                   Python 运营账本 ↔ 无头 SUMO
                                              ↓
                                 原始输出、事件、指标与时间块
                                              ↓
                   Simulation Canvas 回放 / Geo 静态成果 / Document 报告
```

Pi 组织实验并解释结果。Host 按冻结计划和持久 conversation 核验归属、资产、预算、作业与提交，live Pi ID 表示当前运行实例。Python 接收显式配置和文件，经集中 TraCI 适配驱动 SUMO，计算可独立于 LLM 和地图执行。

Traffic Simulation 携带 Skill、Extension、计算脚本和平台运行时。产品采用 CAD 的新任务选择方式，具备匹配 SUMO 运行时的桌面构建随主程序提供仿真能力，用户在新任务中显式选择。依赖仿真的已启用示例也按需选择。既有会话沿用冻结的模块来源、版本与运行时哈希。示例 Data Module 提供有版本的网络和合成输入。

P0 比较过 AgentSUMO 执行层的适配成本，并以真实运行验证直接调用 TraCI 的路线。引擎选择和依赖核查见 [P0 记录](<交通仿真与优化能力升级 P0 记录.md>)。

### 3.2 Agent 工具与作业契约

| 已接入工具 | 用途 |
|---|---|
| `traffic_prepare_scenario` | 检查并冻结场景。受支持的变体通过父场景和声明的干预建立 |
| `traffic_run` | 持久受理后派发受管作业，生成 Run 和可打开的 Simulation Canvas 引用 |
| `traffic_execution` | 查询原执行的状态、进度与提交事实，或请求取消 |
| `traffic_query_results` | 按 Run、时刻、对象和查询边界读取结果 |
| `traffic_experiment` | 准备或查询配对实验清单及比较报告。实际运行经 `traffic_run` 逐槽位派发 |

工具契约由批准绑定生成。Host 从已授权输入派生版本化 Job Manifest，业务参数包含网络、需求、服务、种子、时域、单位与策略。真实路径、运行时、输出根、必要环境和预算由 Host 决定。Python 复核清单，输出带版本、覆盖范围及终止原因的结果。输入与输出按真实路径、授权根和 SHA-256 核验，运行使用显式子进程环境。

### 3.3 执行确认、存储与恢复

执行前记录操作、Run 和工具调用关系。受理、运行、确认中和结束分别可查询，无法确认时保留 `unknown`。成功提交依赖 Host 对最终时刻、原始 tripinfo、车辆与服务计数、指标、索引及文件哈希的复核。取消沿 Pi 信号与受管 Job 确认 Python/SUMO 退出，确认前保留租约。

工作区元数据分别保存冻结场景与几何、Run 的作业清单及原始输出、分块索引与结果清单、实验的冻结 JSON/Markdown 成果。执行确认沿 Host 私有记录和持久归属管理。响应丢失、Host 重启或呈现失败时查询原 Run。相同操作按原记录去重，未知或未确认槽位保留。

### 3.4 完整时间块与 Canvas

Python 写完块文件并记录大小和哈希后原子发布索引。每个块可独立恢复，包含身份、范围、序号、起始状态、采样帧与必要事件引用。起始状态用于恢复，事件只记录一次。故障时保留已发布的完整前缀，索引标明数据覆盖与最终提交状态。Host 经 WebSocket 通知索引变化，Canvas 按需经授权读取，切换会话或 Run 后隔离迟到响应。

计算时刻、已发布时刻和观看时刻分别显示。暂停或隐藏只停止观看。重新显示、刷新或断线恢复时按索引读取，历史结果可在 Pi 未启动时打开。画布按固定 Run、时刻、帧和对象构造 Host 核验的上下文。插值仅用于显示并受实际路径与连续采样约束，业务事件与指标仍对应已发布状态。

Simulation Canvas 与 Geo 共享挂载、地图数据源和相机等基础能力，各自拥有视角、选中状态和资源生命周期。仿真帧使用独立序号，Geo scene revision 与 Pi 历史独立更新。静态指标可走普通 Geo 的发布入口，实验报告复用 Document。

### 3.5 运行时与预算

内部验收包包含 SUMO、netconvert、duarouter、必要 typemap、投影数据与经验证的 Python 依赖。平台运行时与打包配置集中在 `desktop/scripts/platform-profile.mjs`，正式分发按第 6.2 节独立验收。

当前产品配置每工作区最多一个活动 Run，单 Run 上限为 600 仿真秒、120 辆背景车、100 名旅客。计算墙钟预算为 60 s，准备阶段网络检查为 120 s。单 Run 输出上限为 64 MiB，单块与单组事件分别有 2 MiB 读取上限。扩大规模前记录硬件、版本、步长、采样率及活跃人数和车辆数，分别测引擎推进、Host 读取、画布可见延迟、播放帧率与资源占用。

## 4. 数据、指标与方案比较

### 4.1 输入与空间映射

| 输入 | 准备内容 |
|---|---|
| 路网 | 几何、车道、转向、信号、权限、限行、背景交通与外部行程边界 |
| 服务与车队 | 节点位置、候车容量、泊位、步行连接、线路、站序、班表、运能、车辆初始状态与周转 |
| 需求 | 到达时刻、起点、目的地、人数、方式偏好与初始状态 |
| 校准观测 | 有权限和有效日期的到达、队列、发车、载客、运行时间及车队周转 |

网络、需求与服务输入分别冻结版本或哈希。只改班表、车队或需求时可复用已核验路网，改变拓扑、车道或权限时重建并校验映射。路网可来自已有 SUMO 文件或授权 GIS/OSM，班表可用结构化文件。记录源坐标系、投影、偏移、单位和转换版本。地图显示使用 WGS84，车辆位置与车道沿程距离分别解读。公开资料和未核验值按实际来源标注，作为假设的输入留档。

### 4.2 指标口径

道路指标包括入网、到达、未完成、速度、运行时间及道路损失。运营指标包括各点与方式的候车、等待均值及 P90、累计服务与全链完成、末班未接续、滞留、实际趟次、车队占用、载客率和周转。视图和报告标明观察窗口、单位、分母与未完成样本的截尾规则。

等待按实际定义区分枢纽与全程，计划停站与道路损失分别报告。运行中的指标绑定已发布时刻，配对报告的终点指标绑定完整 Run。数值为零、未启用、缺失、未发布分别显示，输入来源和校准状态随结果保留。

### 4.3 配对实验与复现

冻结共同需求、初始状态、背景交通、时域与配对种子，逐项声明允许变化的车队、班次、路径或规则。新增运力同时报告资源成本。当前实验支持基线与一个变体、至多三个配对种子，共六个 Run、3600 仿真秒及每 Run 的输出预算。槽位顺序执行并关联原结果，未确认和不完整配对保留供诊断。

比较清单记录输入、干预、种子、代码、Run、网络、结果哈希与指标口径。敏感性试验用少量明确参数值形成独立变体，报告样本数、差值与未完成状态。真实运营收益需另行校准与验证。

### 5.4 同一 Run 的地铁线路、列车与班表

**先做可行性探针。** 选一段地铁线路，覆盖始发、至少一个中途停站和终到。校验轨道连通、方向、车型通行权限及站台可达性。上海 OSM 路段可作为候选，班表和车型参数可使用明确标注的合成值。探针要证明道路车辆与地铁列车可在同一 SUMO Run 内执行，并保存可关联的实际入网、到站、停站和离站记录。先用可控样例验证计划时刻调整，再用晚到或阻塞样例核对实际偏差。探针通过后接入受管平台 Run，复用 SUMO/TraCI、场景冻结和时间块。

**显式配置两种模型。** 有限班次服务模式沿用班次账本。实体列车模式由场景明确选择，读取已核验的轨道、站台和列车服务记录。历史 Run 按其原协议和账本回放。位置帧缺失按覆盖状态处理，模型语义由冻结配置决定。

**冻结线路、班次、列车和站台映射。** 线路 ID 绑定方向和轨道边序列。班次 ID 对应特定服务日期、线路和站序，独立于列车 ID。列车 ID 映射到 SUMO 车辆并关联其承担的班次。同一列车承担多个班次时，Host 校验时段不重叠。站台 ID 绑定轨道车道和停靠位置，站序区分同一班次重复停靠。旅客接续和服务事件关联 Run、班次、站台及站序，实际停靠事件同时保留列车 ID。

| 内容 | 首版约定 |
|---|---|
| 可调班表 | Agent 经现有结构化场景工具提交班表变更，Canvas 提供轻量表格查看、少量参数编辑与提交。输入包括服务日期、时区、`HH:mm:ss` 计划到发和最小停站时长。首版以 1 s 编辑，运行使用单调仿真秒。Host 校验站序、时间、跨午夜、仿真窗口和列车资源，冻结新变体后另开 Run |
| 计划、约束与实际 | 计划到发是对照基准。SUMO 按最早离站与最小停站时长执行约束，入网和运行条件可以推迟实际结果。分别记录计划始发、实际入网，以及各站实际到站、停站和离站。位置与实际事件由 SUMO 确认。依据见 [SUMO 班表与停站](https://sumo.dlr.de/docs/Simulation/Public_Transport.html) |
| 旅客接续 | SUMO 是列车运动和实际停靠的权威，Python 是旅客、容量、服务事件与接续的权威。实体模式下，Python 按已确认的实际停靠与服务窗口处理上下车，按实际离站确认承运，沿班次和停靠序号核对同一旅客只承运一次。计划时刻只用于班表与约束。明确同秒到达、服务关闭和实际离站的处理顺序 |
| Canvas 显示 | 独立显示线路、站台和列车。列车位置与方向取同一 Run 的轨道采样，明确区分行驶、站台停靠和区间停车。点击列车或站台并列查看计划/实际到发、停站时长、偏差和关联班次。位置轨迹可继续按 2 s 采样，秒级到离站事件单独记录并可定位，界面标出实际展示的帧时刻 |

**班表验证。** 专门设计一组无阻塞、时刻可实现且满足最小停站时长的同线路配对，只改一个计划离站时刻 1 s，核对仿真实际离站的差值。仅在这些条件成立时预期差值为 1 s。差值未达到预期时保存实测值和原因，重新核查该控制样例的可行性。晚到、入网受阻和站台阻塞用独立样例验证计划偏差、容量、旅客接续及窗口结束状态。

**集成验证。** 按 Run、班次、列车和停靠序号交叉核对引擎记录、`tripinfo`、`stop-output`、Host 查询与 Canvas。验证上下车和容量守恒，包括同一实际停靠状态重复读取时的去重，以及计划与实际到发分别展示。保存 Run、事件、帧和截图，复验历史班次模式。完整信号系统、折返、全网调度和实测运营误差按各自用例验证。到离站输出依据见 [SUMO Stop Output](https://sumo.dlr.de/docs/Simulation/Output/StopOutput.html)。

### 5.5 地图布局与指标配置

Simulation Canvas 以地图为主视区。顶部指标横排，图层、底图、图例和视角操作在地图内。时间轴和数据进度固定在地图下方。对象、事件、班表和配对结果放入同一个可滚动的底部抽屉。抽屉支持折叠、默认、展开和拖动调整，短窗口优先保留地图与时间轴。布局变化复用原地图实例，并保留观看时刻、视角、对象和图层设置。

默认指标随已发布数据选择。纯道路 Run 展示在网、零速和累计入网，有限多方式 Run 展示在网、候车、累计完成全链和累计未接续，实体地铁 Run 展示在网、地铁在途、待接续和累计未接续。当前值和累计值都以时间轴标出的已发布位置帧为边界，累计未接续按该帧及之前的接续失败事件对旅客去重。完整 Run 的终点统计在详情中标出全程时间范围。对象详情取自用户选择与同刻查询。

后续为 Agent 增加经 Host 校验的任务视图配置。配置引用已批准的指标、对象类型与图层 ID，由 Host 核验 Run 的数据可用性、单位和统计范围。用户可固定选项或恢复模型默认视图。视图配置与仿真输入、Run 数据分开保存。验收使用同一 Run 切换视图，核对数据和回放结果一致。

布局验收已在上海实体地铁 Run 的已测窗口内通过。1600×1050 下，地图占 Canvas 内容高度约 47% → 73%，折叠详情后约 86%。短窗口、时间轴、地图实例与视角保留、历史 Run 和普通 Geo 的证据见[实施记录](<交通仿真与优化能力升级 P3–P4 实施记录.md#simulation-canvas-布局与默认指标>)。后续沿用这套布局。多硬件、大规模对象和更小窗口分别验收。

| 先做 | 对象联动与指标口径 | 从地图、对象详情和实际到离站事件切换车辆、线路、站台，核对同一 Run 的选中对象与视角。快进、回退及跳转到非采样秒时，当前值和累计值均取对应已发布帧，全程值单列，仅完整结果可用时显示。复验纯道路、有限班次与实体地铁。 |
| 随后 | 动态交通表达 | 按缩放与选择状态调整线路权重，保留道路可读性。用同帧速度、方向和实际站台停靠区分列车行驶、停站及区间停车。选中列车可回查轨道区段与班次，公交载客和节点候车、接续人数可追溯到同帧状态。 |
| 随后 | Agent 任务视图 | 使用地铁晚点、公交增班两个任务，在同一 Run 推荐相关指标和图层。Host 拒绝未知 ID 或 Run 缺少数据的配置。用户可接受、调整、固定及恢复默认，运行异常、样本缺失和覆盖范围持续可见。用真实 Pi、Host 和 Canvas 验证推荐、拒绝和恢复。 |
| 后续 | 多 Run 比较与规模验证 | 复用现有配对结果，按同一统计口径对照路线、事件和指标，保留未完成槽位。逐档增加对象与线路，记录窗口、硬件、帧延迟和资源用量，并复验普通 Geo。 |

## 6. 后续方向与验收

### 6.1 数据关联与 Agent 分析

维护数据需求清单，登记公交和地铁线路、站台及节点设施、班表、发车与停站观测、运行时间和到达客流的来源、有效日期、权限与缺口。取得数据后，用一组历史日期校准队列、发车、载客、运行时间及周转，再以独立日期验证。误差门槛按数据质量和用途提前设定，保留数据缺口及关键参数的敏感性结果。

完整方案推演在第 5.2 节的定位与查询闭环之上推进。以“增配接驳车如何影响积压”或“提前地铁发车会怎样影响接续”为任务，沿既有工具建立独立变体和 Run，报告接续、等待和运力成本，并链接冻结证据。

### 6.2 自动优化与正式分发

有可验证输入后再评估候选优化、运行状态驱动推演和滚动控制。目标按等待、全链完成、末班接续、滞留与运力成本设权重。求解器输出候选方案，记录可行性与终止原因，经独立 Run 比较。在线控制另验决策时刻、可见信息、写命令与恢复。

下一轮优先使用固定快照与可核验线路。通用区域导入需有站点、车道、信号和限制关系核查。扩容按活跃车辆、服务节点和采样率分档实测。现有样例的规模与完成率记录在阶段证据中。

正式分发与下载另行安排。发布前在目标平台的干净环境验收主程序安装、仿真默认未选、手动选用后的真实运行、历史恢复、许可与签名。当前本地集成使用 macOS arm64 的 SUMO 运行时，Windows 与 Linux 以各自运行时证据为准。复杂三维城市、全城实时交通、室内行人和精细轨道模型按实际用例另行评估。

### 6.3 回归与验收记录

| 检查面 | 验收重点 |
|---|---|
| 装配与执行 | 真实安装、信任、Pi 调用、Host 作业及 SUMO 输出。核对授权、输入边界、重定位、取消、异常、提交与恢复 |
| 模型与比较 | 核对同刻顺序、资源守恒、满载、跨午夜、返场和末班接续。保留全部未完成对象与配对槽位 |
| 回放与普通 Geo | 核对计算中打开、时间块恢复、同刻查询、切换 Run/会话、历史重开及迟到响应隔离。复验普通 Geo 的选区、截图、图例和附加上下文 |
| 证据与性能 | 对照实际 Run、时间块、事件和指标。记录观看延迟、播放表现、资源占用、截图、测试结果和待验项 |

下一轮固定复用 P0 纯道路、P2 多方式及三种子配对、上海 600 s 回放、历史和部分 Run。实体地铁验收追加独立场景与班表变体，覆盖运行、停站和接续。每项新增功能以相关案例验收。

实施前运行 `npm run test:budget`，将新断言合入既有关键场景，Node 实际注册总数不超过 40。以实际运行验收执行链和模型行为，软件回归、真实运营校准及成品分发各自保存证据。
