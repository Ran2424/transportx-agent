## 1. 方向与首版范围

将 **TransportX Traffic Lab** 建设为独立可安装的业务 Module，拟用 ID 为 `com.transportx.traffic-lab`。复用 Electron / React 工作台、Geo Capability、Pi 工具编排和 Node Agent Host，增加交通实验能力。

首版目标是完成以下闭环：

```text
地图选择研究区域 + 路网/需求/站点输入
    → netconvert / duarouter 构建并校验 SUMO 场景
    → 无头 sumo + TraCI 基线仿真与交通状态采集
    → 路网成本矩阵 → OR-Tools 求解
    → 校验方案 → 准备独立优化 Run → 启动无头仿真
    → TransportX GIS 展示与可追溯对比报告
```

本次将以下首版范围固定，变更时需更新对应阶段的验收标准：

- 第一个业务场景为**大型活动周边接驳车辆的站点任务分配与访问次序优化（带容量和时间窗的 VRP）**。任务具有需求量、服务时长和时间窗，车辆具有起终点与容量；首版不做成对乘客接送、即时叫车或多趟滚动调度。
- 首版求解目标为在全部必需站点任务满足容量、时间窗与可达性约束的条件下，最小化车队总路网旅行时间。默认不允许求解器静默丢弃站点；无可行解时保留诊断，软时间窗、多目标权重和弃单罚分后置。
- 采用本地无头 `sumo`，由 Python Worker 维护 TraCI 连接；Agent 调用业务工具，不直接操作 TraCI 底层接口。二维地图先做道路、站点、路线与统计快照，按需刷新；逐车逐帧动画、三维展示与时间播放后置。
- 首版采用离线方案对比：基线运行完成后求解，再在独立 Run 中应用方案并重跑。暂不做运行中车辆的连续重调度。
- 第一轮交付先完成 P0–P2，证明模块、路网和有状态仿真贯通；P3–P4 才形成优化闭环。正式分发还须通过 P5。

本轮复用现有 Pi Harness 与地图交互，不建设独立仿真工作台、第二套 Streamlit/Folium UI、Agent Loop、Planner、Agent State、通用 MCP Server、第三方 Host 插件容器或公共求解器框架。自适应信号控制、强化学习、多 Agent 控制、远程仿真集群及其他求解器均后置。

### 1.1 用户操作与首版完成定义

1. 用户在 TransportX 地图选择/确认研究区域和站点，关联固定本地 OSM、合成需求及车队；Agent 通过 `inspect_map_context` 读取上下文并确认缺失输入。
2. 创建场景后在现有地图展示道路、站点及可达性诊断；点击路段可查看 SUMO Edge ID、方向、限速和车道属性。
3. Agent 启动无头基线 Run，连续推进并读取状态，在同一工作台按需刷新路段指标和站点服务快照。
4. 基线结束后调用 OR-Tools，展示求解状态与方案验证结果；将已验证方案准备为独立优化 Run，再启动并完成仿真。
5. 检查两组输入与指标口径，输出路线/路段专题图、未服务任务、异常和报告依据。

**首版完成定义**：上述固定样例从自然语言与 GIS 选区到对比报告全程贯通，进程链中没有 `sumo-gui`，查看与选择均在 TransportX 完成。地图标签关闭/重新打开不改变 Run 生命周期和仿真时间。结果允许无改善或变差，但须与原始状态、路径、指标及输入版本一致。

## 2. 当前基础与需要补齐的缺口

以下为源码核查结果；讨论中的目录、清单示例和服务名称均不能直接视为已支持接口。

| 已有基础 | 当前限制 | 后续升级 |
|---|---|---|
| Geo 支持地图上下文、GeoJSON 发布和 revision 化展示 | GIS 几何不包含完整的仿真拓扑、交通规则与需求 | 增加 Traffic Network Adapter，分开管理展示路网、仿真路网和求解输入 |
| Module Manifest v2、Registry、Installer 与 Session Plan v3 | 安装 Module 不会自动增加 Host 服务或授权 | 复用安装装配；为 Traffic Lab 增加平台批准的领域操作和会话授权 |
| `PythonRunner.run()` 提供单次脚本的超时、取消和进程回收 | 无跨工具调用的长驻 TraCI 命令会话 | 增加 Host 管理的仿真 Worker 生命周期与逐 Run 命令串行化 |
| 基础 Python 包含 NumPy、Pandas、PyProj、Shapely 等 | requirements 未声明 `traci`、`sumolib`、`ortools`；SUMO 本体也需单独准备 | 验证模块专属 Python 环境及 SUMO 原生运行时，不向基础 Python 隐式安装依赖 |
| Module 已有 Native Runtime 声明、完整性检查和计划解析 | 当前 `kind` 与可执行项专用于 ffmpeg/ffprobe | SUMO 分发前扩展 Manifest、Installer、Assembly、Plan 与恢复校验，不能只改包清单 |
| Pi 历史、Canvas、Geo 资源和 Citation 已能承载成果 | 没有交通实验对象、指标口径与可比性校验 | 增加实验清单和领域结果；对话历史、地图 scene 与引用沿用既有权威 |

核查入口：[Geo Extension](../modules/capabilities/geo/extensions/pi-geo-visualization/index.ts)、[PythonRunner](../src/server/python-runner.ts)、[ProcessRunner](../src/server/process-runner.ts)、[Python requirements](../desktop/python-requirements.txt)、[Module 契约](../src/contracts/module.ts)、[Resolved Session Plan](../src/contracts/resolved-session-plan.ts)、[Session Service 授权映射](../src/server/session-service.ts)。

需重点补齐两层：**Traffic Network Adapter** 解决网络模型、坐标和 ID 转换；**Traffic Experiment Runtime** 解决 Run 状态、受控执行、方案应用、结果比较和复现。

## 3. 组件职责与平台边界

| 组件 | 责任 | 边界 |
|---|---|---|
| GIS / Geo Capability | 研究范围、道路与站点交互、路线和指标图层展示 | 不承担微观仿真或求解；不迁移现有 Geo scene 状态 |
| 无头 `sumo` | 车辆运行、仿真推进与交通状态计算 | 独立原生进程，不启动或依赖 `sumo-gui`；不负责地图渲染 |
| netconvert / duarouter | OSM 转网、基于需求生成可行驶的初始路线 | 不负责 Agent 编排或用户界面；不得擅自改变已校验优化方案的停靠顺序 |
| sumolib / Network Adapter | 读取网络、坐标转换、拓扑与 Edge 映射、路径成本 | 输出有方向、车辆类型和时间口径的网络数据 |
| TraCI / Python Worker | 保持连接、读取状态、推进仿真、应用受支持命令 | 每个 Run 的连接由 Worker 独占；不向模型开放任意 Python/TraCI 执行入口 |
| OR-Tools Routing / Optimization Adapter | 在明确目标和约束下计算任务分配、停靠顺序 | 不负责微观仿真；求解输出必须再次通过道路可行性校验 |
| Pi Extension / Skill | 参数收集、调用编排、解释结果和局限 | Pi 继续负责工具注册、调度与历史；Skill 说明不代替 Host 输入校验 |
| Node Agent Host | 会话授权、Worker 与作业生命周期、结果提交和受控读取 | 不动态 import 安装包中的 Host 服务代码；不开放任意服务地址 |

`sumo` 是命令行仿真内核，网络/路线文件、TraCI 和输出文件能够提供本场景所需的计算与数据；TransportX 自己消费这些数据进行展示。[SUMO 官方说明](https://sumo.dlr.de/docs/sumo.html) 地图重绘不驱动仿真时钟，地图关闭不隐式取消运行；任务停止/删除仍须进入 Host 清理流程。

接入方式分两步：

1. P0–P1 的环境诊断、离线网络转换可先通过受信任的 Pi-local Extension / 脚本验证。安装可执行 Extension 仍涉及本机代码执行，不能描述为操作系统沙箱。
2. P2 持续仿真必须由平台代码提供领域 Service、固定操作入口和服务授权，明确 Traffic Lab 消费方身份及计划归属；不能借用 Spatial/Video 的 token 或模块 ID。模块未安装或未装配时不启动 Worker。

本计划不要求先完成 Tool PLAN 的全部阶段。当前已有代码信任入口和 Citation/Spatial 工具契约、薄客户端试点，接入时应核对并复用其已验收部分；进行中的 Spatial 持久执行改动不能直接视为已发布的通用保障。Traffic Lab 仅补本场景必需的领域确认与恢复语义，不另建平行 Contract、Binding 或 Invocation 系统。两份计划中的 P0、P1 等编号各自独立。

## 4. 功能升级清单

### F1. 模块安装、运行环境检查与就绪诊断

- 声明 Skill、Pi Extension、依赖与成果类型；最小直接依赖包括 Geo，Citation 用于报告依据。只有实际调用受控空间分析时才增加 Spatial Analysis，避免仅为模仿示例而依赖。
- 检查 Python 及 `traci` / `sumolib` / `ortools` 导入，`sumo` / `netconvert` / `duarouter` 的版本、实际路径、可执行性和 TraCI 兼容性；P0 固定验证版本组合及锁文件。安装 Python 客户端不代表 SUMO 本体就绪，诊断不能通过启动 `sumo-gui` 验证环境。
- 开发验证允许用户显式指定本机 SUMO 与模块专属 Python 环境，记录实际路径、版本和哈希；不依赖开发者个人目录、Conda 或隐式 PATH 搜索作为发布条件。
- 区分“模块已安装”“本会话已装配”“运行环境已验证”。诊断通过现有能力概览投影；启动操作仍需核对实际环境，不能只信任 UI 状态。

**验收**：按现有安装入口导入和启用；缺失程序、依赖不兼容、模块未装配时返回具体原因，平台其他能力仍可使用。

### F2. 研究区域与可仿真场景构建

- 从现有 Geo Context 获取范围与站点，关联用户提供的 OSM/道路拓扑文件；地图底图和任意道路 GeoJSON 不自动等同于可仿真输入。
- 首个样例使用固定的本地 OSM 输入，避免网络下载变化干扰验收。在线取数可后续加入，并记录来源、时间与原始文件版本。
- 调用 netconvert 构建 `.net.xml`；补齐或显式标记车道、转向、限速、通行权限、信号、车辆类型和交通需求中的缺失项。SUMO 官方提供 OSM 转网能力，但导入结果仍需检查。[官方说明](https://sumo.dlr.de/docs/Networks/Import/OpenStreetMap.html)
- 由需求生成脚本与 `duarouter` 生成初始 `.rou.xml`，写出 `.sumocfg` 和站点停靠配置；记录需求生成种子、路由参数与工具版本。`duarouter` 用于从需求计算 SUMO 可读取的车辆路线。[官方说明](https://sumo.dlr.de/docs/duarouter.html)
- 保存网络、需求、车辆、站点、仿真时段、步长、种子和生成参数。站点应映射到允许车辆停靠的道路/车道位置，不能只保存经纬度。
- 研究范围裁剪后校验边界出入口和连通性；不可达站点、断路及推断的道路属性应形成诊断。合成需求须明确标识，不能作为真实需求预测。

**验收**：固定样例可由无头 `sumo` 加载，TransportX 地图可查看网络与站点，全程不调用 `sumo-gui`；缺少关键拓扑或需求时明确拒绝，报告推断字段和未匹配对象。

### F3. GIS—SUMO—求解网络适配

- 分开保存 GIS 几何、SUMO 有向车道/连接拓扑和求解用站点/OD 成本；共享来源，不强行共用一个数据结构。
- 建立可双向查询的 `EdgeMapping`，支持一对多、多对一、方向、道路切分及无对应 GIS 要素的 SUMO 内部连接；不假设 ID 相同即对应。
- 为当前网络建立站点/道路属性交叉索引，支持“GIS 选中要素 → SUMO Edge/Lane → 属性与结果”查询；道路名称只返回候选，方向或匹配不唯一时须确认具体 Edge，不用名称相似度代替映射，也不为此预建 RAG/向量库。
- 记录原始 CRS 与 SUMO 网络投影/偏移，按网络元数据转换；输出给 Geo 的数据统一为 WGS84。SUMO 的 sumolib 提供网络读取和经纬度转换接口。[官方说明](https://sumo.dlr.de/docs/Tools/Sumolib.html)
- 基于可行驶拓扑生成有向 OD 成本矩阵，记录车辆类型、成本单位和时间窗；不可达 OD 显式标记，不能填 0 或用直线距离代替。
- 将求解停靠顺序展开为合法 Edge 序列，复核连续性、方向、通行权限和停靠位置。无可行路径时拒绝方案应用。

**验收**：覆盖单行道、道路切分、内部连接、不可达站点和坐标往返样例；从 TransportX 地图选中道路可核对 Edge、方向、限速及车道，每项结果可追溯到网络版本。坐标容差在 P0 根据样例确定并在 P1 验证。

### F4. 有状态 Simulation Run 与受控执行

- 一个场景可以创建多个独立 Run；每个 Run 绑定所属任务、场景版本、进程、连接、种子、当前仿真时间与状态。
- Host 启动目标固定为无头 `sumo`；运行时配置不能切换到 `sumo-gui`。快照和成果来自 Worker/输出文件，不能依赖显示窗口、截图或渲染帧生成。
- 首版同一任务最多一个活动 Run，基线与优化顺序执行；不提前建设批量并行调度器。跨任务仍须纳入 Host 总资源预算，不能绕过既有子进程限制。
- Host 通过受控本地通道向 Worker 发送固定命令，TraCI 连接及其端口仅供本机内部使用，不作为用户/模型接口。TraCI 用于控制正在运行的仿真，适合由持续连接承载。[官方说明](https://sumo.dlr.de/docs/TraCI/index.html)
- 同一 Run 的命令串行处理。工具调用之间保留进程与仿真时间；仅显式 `step` 推进，限制单次步数、墙钟耗时和返回体量，禁止后台无限推进。
- 任务停止、删除、Host 退出时停止 Worker 与 SUMO 进程树，等待关闭和输出落盘；端口与临时文件释放后才确认清理完成。无法确认退出时返回未确认状态。
- Host 异常重启后读取已有清单，将未确认结束的 Run 标记为中断；核查与清理残留资源，不自动续接未知 TraCI 状态，不盲目凭旧 PID 杀进程。首版不承诺检查点续跑。

**验收**：真实 Pi→Host→无头 SUMO 依次启动、读状态、连续两次推进、再读状态、停止，连接与仿真时间延续；并发命令、重复 start/step、超时、响应丢失、取消、Worker 崩溃和任务退出均能核对状态与资源。检查实际启动进程及参数，确认没有调用 `sumo-gui`。

### F5. TransportX GIS 状态快照与结果展示（P2 / P4）

- `traffic_get_state` 默认返回有界摘要：仿真时间、在网/完成车辆数、路段速度、等待与旅行时间，以及采集窗口和单位。
- 状态输出区分当前快照与区间统计；排队、等待、延误分别定义，缺失值不能当成 0。只实现首个业务场景实际需要的指标。
- 需要空间分布时，生成任务内 GeoJSON，沿用 `publish_geodata → present_visualization`；模型接收摘要与资源引用，不接收逐车逐步的完整轨迹。
- 地图展示基线/优化路线、站点和速度或拥堵指标，按需刷新；不逐仿真步推送全量 GeoJSON。遵守 Geo 现有要素数、大小限制及三主题 token 规则。
- P2 交付网络/站点底图、路段统计与站点服务快照；P4 补充基线/优化路线差异和同口径专题图。图层标明场景/网络、Run、采集窗口与版本，选中道路可查看对应指标。路口/信号位置可作为属性展示，不包含信号编辑器或控制优化。
- 首版不新增逐车动画 Canvas Adapter 或 GeoScene 播放协议；时间滑动条、抽样轨迹和实时动画需后续单独立项，以业务用途及实测预算决定。

**验收**：仅通过 TransportX 地图即可选路、刷新状态和查看对比，工具摘要、原始指标和图层统计相互一致；关闭地图标签或浏览器断开不推进/停止 Run，重新打开仍能读取已保存的成果和时间窗口。

### F6. 接驳车辆路径与调度求解

- 首个模型固定为站点访问 VRP，含车辆起终点、站点需求量、容量、服务时长、硬时间窗与可达性；目标按第 1 节最小化车队总路网旅行时间。首版每项必需任务完整分配给一辆车一次，不做拆分、成对接送或默认弃单。
- 容量模型按单趟所分配非负任务需求总量不超过车辆容量表达；P0 将样例固定为与之匹配的单向集散，不将其解释为一般站间上下客。时间窗定义为服务开始时刻，计入提前到达等待和服务时长；需求、容量、时间统一单位并记录求解器整数缩放/舍入规则。[容量模型参考](https://developers.google.com/optimization/routing/cvrp)
- 首版用指定时段的静态行程时间矩阵，来源可以是道路自由流成本或基线采集结果，必须标注。动态拥堵反馈由重跑验证，不声称静态矩阵等价于时变最优控制。
- OR-Tools 接收成本矩阵与约束，返回分配和访问顺序；道路路径转换由 Network Adapter 完成。[VRP 官方说明](https://developers.google.com/optimization/routing/vrp)
- 结果保留求解器原始状态，并分开表达“有无可行解”“是否证明最优”“终止原因”。支持可行、已证最优、已证不可行、超时、未找到解、模型无效、取消与执行失败；不能把成功求解一概标成最优，也不能把未找到解等同于已证不可行。[状态与搜索限制](https://developers.google.com/optimization/routing/routing_options)
- 超时仍有解时保存为候选，经过约束与路径校验后才允许显式应用；无解或未经验证的方案不得进入仿真。记录时间上限、搜索配置、随机性设置和耗时。
- 方案除 Edge 路径外还须生成站点停靠、服务时长与等待安排，并在仿真中采集实际服务开始/结束事件；不能仅让车辆经过站点就记为服务完成。求解预计可行与拥堵下实际违约分别记录。

**验收**：固定小样例得到可核对的容量与时间窗可行方案；不可达、已证不可行、超时有解和超时无解等分支均不误报最优或成功应用。

### F7. 方案应用、实验比较与报告

- 方案绑定输入场景/网络/需求版本、成本矩阵和约束摘要。应用前复核归属、哈希和路径，禁止跨会话或将旧方案套入已变更网络。
- 首版在 SUMO 启动前应用方案：`traffic_apply_plan` 核验后生成独立优化 Run 的配置与路线，返回 `CREATED` 的 Run ID；再由 `traffic_start_simulation` 启动。拒绝对已启动的 Run 覆盖方案，避免把“尚未 step”误认为可以直接替换已加载的路由；基线保持原样。
- 基线使用预先固定的车辆—站点分配与访问顺序，记录生成方法，不临时挑选有利基线；与优化组使用同一服务/等待规则。基线及优化各自的实际服务事件进入完成率和违约统计。
- 比较前校验共同输入：网络、外生背景需求、待服务任务、车队、仿真时段、步长、种子与指标口径。方案改变的分配/路线作为实验变量单独登记，不能要求两组路线文件哈希相同。
- 输出总/平均旅行时间、等待时间、服务完成率、时间窗违约与未服务任务数；每项指标注明对象、单位、统计窗口和分母。两组同时记录未完成车辆、未发出车辆和异常传送等情况，避免只比较成功到达车辆造成偏差。
- 展示基线值、优化值和差值；基线为 0 时不计算普通变化百分比。允许优化无收益或变差，求解目标改善不能代替 SUMO 验证结果。
- 保存实验清单、原始指标、地图数据和报告，使用现有 Citation 登记输入版本及结果依据；引用登记失败保留计算成果并明确警告。

**验收**：同一固定需求完成基线→求解→应用→优化重跑→对比报告；输入不一致时标为不可直接比较，不输出改善结论。单种子用于闭环验收，业务效果评估应另做多种子重复实验，不据此宣称真实交通收益。

## 5. 最小数据契约与成果存储

以下为待实现的领域对象，不是现有公开协议。实施时由平台共享契约承载跨层部分，模块脚本遵守同一格式；不要维护相互漂移的 TS/Python/JSON Schema 定义。

| 对象 | 最小记录 | 作用 |
|---|---|---|
| `TrafficScenario` | ID/版本、所属任务、范围/CRS、输入哈希、网络/需求/车辆/站点引用、时段、步长、种子、生成参数 | 确定场景和实验共同输入 |
| `RoadGraph / EdgeMapping` | 网络哈希、有向边/连接、车辆权限、GIS ID ↔ SUMO Edge/Lane 对应与转换信息 | 维护网络版本与空间关联 |
| `SimulationRun` | Run ID、场景引用、方案引用、状态、仿真时间、运行时版本/哈希、开始/结束原因、结果引用 | 唯一记录仿真运行事实 |
| `TrafficState / CostMatrix` | Run/网络引用、采集窗口、车辆类型、指标/成本单位、缺失与不可达标记 | 防止混用时间、单位和可达性 |
| `OptimizationPlan` | Plan ID、输入哈希、任务模型/约束、求解配置与状态、目标值、访问顺序、Edge 路径、验证结论 | 区分候选方案和可执行方案 |
| `ExperimentResult` | 基线/优化 Run 引用、共同输入校验、指标口径、对比值、异常记录、地图/报告/依据引用 | 支撑可核对比较 |

运行中事实以 Host/Worker 确认结果为准，完成成果以已校验的领域清单为准。Pi JSONL 保存对话和工具历史，Geo Extension 继续维护地图 scene；不另建平行历史系统。

成果放在所属任务工作目录内的独立 `traffic-lab/` 子目录，场景、Run 和方案分开保存。持久路径统一 POSIX 相对路径，读取时经过现有路径归属与完整性校验，不接受模型指定任意本机输出路径。

Manifest/Session Plan 当前允许修改 Skill/Extension 内容，不能据模块版本号宣称代码逐字可复现。实验清单还应记录实际脚本、依赖锁定文件、配置与原始输入的哈希；需长期复现时保留对应模块包及数据副本。固定种子也不保证不同 OS/版本逐位一致，比较与复现报告须写明环境和容差。

## 6. Agent 工具边界

保留讨论中约 8 个业务工具的方向，名称为拟议接口；参数、Schema 和 Operation 映射在对应阶段确定，不一次暴露 TraCI 全部 API。

| 拟议工具 | 责任 | 首次交付 |
|---|---|---|
| `traffic_create_scenario` | 校验输入、构建网络与场景、返回诊断和引用 | P1 |
| `traffic_start_simulation` | 创建独立 Run，完成连接与 ready 确认 | P2 |
| `traffic_get_state` | 查询 Run 状态/命令执行确认，按需输出统计与空间成果 | P2 |
| `traffic_step` | 有界推进仿真并返回实际仿真时间和摘要 | P2 |
| `traffic_stop_simulation` | 停止并确认资源回收，保留已提交成果 | P2 |
| `traffic_optimize` | 生成成本矩阵、求解、验证并保存候选方案 | P3 |
| `traffic_apply_plan` | 核对版本与约束后，将方案应用于未推进的优化 Run | P3 |
| `traffic_compare_runs` | 检查可比性并生成指标、地图数据和报告依据 | P4 |

所有 Host 动作均验证会话、模块装配、对象归属、输入版本和参数。创建、推进与应用等有副作用命令需要调用关联与结果查询：同一调用重发返回已确认结果或待核实状态，不能再次推进仿真；新调用 ID 才表示新动作。

响应丢失、取消或超时不等于动作未执行。Host 与 Worker 应记录命令受理和完成确认，按当前 Run 及实际仿真时间核对；无法确认时标记未知/中断，拒绝自动重试 `step` 或 `apply_plan`。取消不能承诺回滚已完成的仿真步。只读查询不为字段统一而创建持久 Job。

## 7. 实施阶段与退出条件

P0–P5 是交付顺序，不代表所有功能同等优先；前一阶段的退出条件通过后才进入下一阶段。

| 阶段 | 交付物 | 退出条件 |
|---|---|---|
| P0：边界与环境 | 最小 Module 清单/诊断、版本兼容矩阵、首个接驳模型、固定输入样例、Host 授权方案和资源预算 | 能安装装配；环境完整/缺失两条路径可核对；确定 Python/SUMO/依赖版本、坐标容差、数据规模和性能上限；P2 所需平台改动明确 |
| P1：网络适配 | GIS 范围→本地 OSM→SUMO 网络→GeoJSON；EdgeMapping 与场景清单 | 地图/SUMO 对应可追溯；单行道、切分、坐标转换及不可达样例通过；SUMO 可加载场景 |
| P2：持续仿真 | 平台领域 Service/授权、受管 Worker、启动/查询/推进/停止工具 | 真实 Pi + Host + SUMO 完成连续调用；隔离、重复请求、取消/超时、崩溃及退出清理可核对；不自动重放未知命令 |
| P3：路径求解 | 路网成本矩阵、OR-Tools Adapter、方案状态/约束/路径校验、应用工具 | 求解与失败分支通过；可行方案可应用于新 Run；不合法、过期或归属不符方案被拒绝 |
| P4：实验闭环 | 基线/优化重跑、可比性检查、GIS 图层、报告与依据 | 活动接驳场景从地图输入到对比报告贯通；指标与原始结果一致；无改善结果如实呈现 |
| P5：分发与回归 | SUMO Native Runtime 契约扩展、平台专属可安装包、安装说明与验收记录 | macOS arm64 / Windows x64 分别通过干净环境安装、依赖/完整性校验、场景重跑和退出清理；不依赖开发机环境 |

P0–P2 是可启动的第一轮开发任务；P3–P4 是首个产品闭环；P5 是桌面可选能力正式交付门槛。P0 需要提前确认双平台原生依赖是否可获得，不能等到 P5 才发现无法分发。

性能预算由固定小场景和代表性场景测量后确定，至少覆盖转网耗时、每次推进耗时、求解上限、Worker/SUMO 峰值内存、结果体量及停止确认时间。记录 OS/架构、版本、数据规模和样本数，不预填没有测量依据的性能数字。

## 9. 验证方式与实施前待定事项

本次文档整理仅核对源码、链接和范围，不作为功能验收。后续实现采用三层证据：

1. 固定小型样例核对映射、坐标、可达性、约束、指标和重复命令语义。
2. 真实 Pi + 生产 Module 装配/Host 路由 + 实际 SUMO/OR-Tools 验证闭环；fake Pi/Worker 可做故障注入，不能代替真实运行证据。
3. 两个平台的桌面安装包在干净环境验证运行时加载、资源校验、停止清理和既有能力回归。Windows 在 Windows x64 主机验收，不在 macOS 交叉打包代替。

改动前先运行 `npm run test:budget`，新断言合并到既有关键场景，总注册节点不超过 40；不以循环、子测试或隐藏 case 列表绕过预算。按实际改动执行类型检查、核心测试、Web 或平台冒烟；不为纯文档变更运行仿真或全量构建。

P0 必须关闭以下待定项，当前不将其写成已完成决策：

| 待定项 | 默认方向 / 决策依据 |
|---|---|
| 首个样例的数据来源、规模与接驳模型 | 固定可分发的本地路网和合成需求；明确站点访问/成对接送、目标函数与验收容差 |
| Python/SUMO/OR-Tools 版本与依赖隔离 | 从 Python 3.10 兼容组合验证；检查双平台依赖与可重定位性，再锁定版本 |
| 平台 Host 操作及包身份授权 | 平台实现固定领域操作，为 Traffic Lab 显式授权；复用 Tool PLAN 已落地机制，不默认拥有任意 Host 扩展权 |
| 运行时契约、恢复兼容与最低平台版本 | 根据新增必需语义决定兼容扩展或协议升级；旧 reader 不能错误接受不支持的 SUMO 包 |
| 可复现成果与模块源的保存位置 | 复用任务工作区与现有模块分发，明确脚本/输入副本和保留策略；不把暂存目录作为唯一来源 |

后续扩展候选包括时变成本与滚动调度、信号优化、批量实验、其他求解器及远程 Worker。只有首个闭环和双平台交付通过后，再按真实需求立项，不预建其抽象层。
