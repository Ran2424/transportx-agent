# 引用板块功能设计

> 状态：阶段一基础闭环已实现
> 更新时间：2026-07-26
> 目标：让 Agent 的回答可以引用知识库依据，以及本次任务生成或使用的报告、PDF、普通文档和图片，并在消息末尾以清晰、可核查的方式展示来源。

## 1. 要解决的问题

当前知识库 Skill 已经可以检索法规、标准、预案、案例和项目资料，也能返回文档名称、条款、PDF 页码和原件路径。

现在缺少的是回答与来源之间的产品连接：

- 用户不知道某个结论具体依据哪一项来源；
- 来源以普通文字输出时，Agent 可能写错页码或文件路径；
- PDF、文档和图片的定位方式不同，不能只依赖一个 Markdown 链接；
- 来源散落在正文里会打断阅读；
- 刷新或恢复会话后，来源信息需要继续存在；
- 法规、标准、预案和案例的效力需要被清楚区分。

因此，本功能的重点不是建设新的知识库，而是把现有检索结果变成对话中的可点击引用。

## 2. 产品形态

一条带引用的回答由两部分组成。

### 2.1 正文中的引用编号

Agent 在相关结论后添加引用标记：

```md
活动承办者发现人群聚集后，应及时安排工作人员疏导。
[[cite:K-GBT33170.2-2016-000058]]
```

界面显示为：

```text
活动承办者发现人群聚集后，应及时安排工作人员疏导。[1]
```

正文只显示简短编号，不直接展开完整来源，避免影响阅读。

同一个来源在一条消息中多次出现时复用相同编号。一个结论同时由多个来源支持时，可以显示多个编号。

### 2.2 消息末尾的“引用依据”板块

消息底部统一展示本条回答使用的来源：

```text
引用依据 · 2

[1] 大型活动安全要求 第2部分：人员管控
    8.4 · PDF 第9页（正文第6页）
    标准要求 · 页面已对齐

[2] 上海市大型活动交通保障预案
    交通疏散章节 · PDF 第18页
    作业预案 · 人工已复核
```

每项来源至少显示：

- 文档或图片名称；
- 条款、章节、页码或图片说明；
- 来源类型；
- 规范强度或资料属性；
- 验证状态；
- 查看原文入口。

来源较多时默认折叠，只展示前几项和“展开全部”。

### 2.3 点击引用后的行为

用户点击正文编号或消息末尾来源时，打开引用详情：

- PDF：显示引用原文、条款和物理页，并可打开对应页面；
- 普通文档：显示章节路径、来源单元、行号和引用原文；
- 图片：显示图片缩略图和引用说明；
- 来源暂时不可打开时：仍显示已经保存的标题、定位和引用原文。

首版不要求在 PDF 或图片上绘制精确高亮框。能进入正确页面或看到对应图片，已经可以完成主要核查任务。

## 3. 核心实现逻辑

### 3.1 Agent 只输出引用 ID

Markdown 本身没有统一的多模态引用标准。不能让 Agent 直接生成文件路径、PDF 地址或图片坐标。

推荐保留简单标记：

```text
[[cite:<knowledge_id>]]
```

例如：

```text
[[cite:K-GBT33170.2-2016-000058]]
```

这里的 `knowledge_id` 已经由知识库提供，比临时的 `s1`、`s2` 更稳定，也不会在多轮会话中混淆。

前端只负责把 ID 转换为 `[1]`、`[2]` 等可读编号。

### 3.2 引用信息由系统保存

Agent 准备引用某个知识条目时，调用一个简单的引用注册工具，例如：

```text
tau_cite(["K-GBT33170.2-2016-000058"])
```

该工具从知识库读取可信信息，并随会话保存：

```json
{
  "citationId": "K-GBT33170.2-2016-000058",
  "source": {
    "sourceId": "GBT33170.2-2016",
    "type": "pdf",
    "title": "大型活动安全要求 第2部分：人员管控"
  },
  "location": {
    "nodeId": "GBT33170.2-2016@8.4",
    "clause": "8.4",
    "page": 9,
    "printedPage": "6",
    "quote": "在监测过程中，发现人群聚集和拥挤现象时……"
  },
  "documentClass": "STANDARD_SPEC",
  "normativeForce": "recommended",
  "verificationStatus": "page_aligned"
}
```

回答中的标记与这份结构化信息通过 `citationId` 对应。

这样可以保证：

- 页码和文档名来自知识库，不由 Agent 编造；
- 引用信息可以随 JSONL 会话历史保存；
- 刷新、历史查看和恢复会话后仍能重建；
- 前端可以统一处理 PDF、文档和图片；
- 浏览器不需要看到知识库的真实绝对路径。

### 3.3 与当前项目的结合方式

项目现有 Geo 和任务模式已经通过 `toolResult.details` 保存结构化结果。引用功能沿用同一条链路：

```text
知识库 Skill
  → tau_cite
  → toolResult.details
  → Pi JSONL / WebSocket
  → React 引用板块
```

不需要：

- 新建数据库；
- 修改 Pi 的基础消息格式；
- 新建第二套 WebSocket 协议；
- 重做知识库索引；
- 整体替换 Markdown 渲染器。

引用数据只是一种新的结构化工具结果。

## 4. 功能需求

### 4.1 必须支持

1. Agent 可以把知识库返回的 `knowledge_id` 注册为引用。
2. 不存在、未验收或没有有效来源定位的知识条目不能注册。
3. Assistant 正文支持 `[[cite:id]]` 和 `[[cite:id1,id2]]`。
4. 前端按消息内首次出现顺序生成引用编号。
5. 同一个引用重复出现时编号保持一致。
6. 消息末尾自动生成“引用依据”板块。
7. 来源按文件或资源分组，避免同一个 PDF 重复显示多张卡片。
8. PDF 显示物理页，正文印刷页作为补充。
9. 文档显示章节、来源单元、行号或稳定节点。
10. 图片可以显示缩略图和引用说明。
11. 点击引用可以查看详情或打开原件。
12. 引用随会话历史保存，并支持刷新和 resume。
13. 未人工复核、原件缺失或来源发生变化时必须明确提示。
14. 复制回答时，将内部引用标记转换成普通编号和来源列表。

### 4.2 暂不要求

- PDF 文字区域精确高亮；
- 图片区域框选；
- 任意 Word、PDF、图片上传后自动建立索引；
- 引用编辑器；
- Markdown 脚注导出；
- 自动判断 Agent 的整句推理是否被原文充分支持；
- 网页快照和外部网页抓取。

这些能力以后可以在同一引用数据结构上增加，但不是引用板块首版上线的条件。

## 5. 不同来源的展示规则

### 5.1 PDF

首版保存和展示：

- 文档名称；
- 条款或节点；
- 物理 PDF 页；
- 可选正文印刷页；
- 引用原文；
- 文档类别；
- 验证状态。

点击后打开对应物理页。

### 5.2 普通文档

首版保存和展示：

- 文档名称；
- 章节路径；
- 来源单元；
- 行号或段落；
- 引用原文。

如果文档有稳定 block ID，优先使用 block ID；没有时再使用章节和行号。

### 5.3 图片

首版保存和展示：

- 图片名称；
- 缩略图；
- 引用说明；
- 可选 OCR 或识别文字；
- 验证状态。

首版可以引用整张图片，不要求提供区域坐标。

## 6. 引用状态与措辞

引用板块不能只显示文件名，还要帮助用户理解来源性质。

| 来源类别 | 展示和措辞 |
|---|---|
| 法律法规与制度 | 可作为法定职责、许可、禁止和监管边界 |
| 标准规范 | 标为“标准要求”或“标准推荐”，不自动写成法定义务 |
| 预案和作业规程 | 标为程序或协同机制 |
| 案例实践 | 只能表述为“曾采用”或“可参考” |
| 国外指南或研究 | 标明方法来源和适用性转换 |
| 项目资料 | 标明项目内数据或指标口径 |

验证状态建议使用容易理解的文案：

| 知识库状态 | 界面显示 |
|---|---|
| `manual_verified` | 人工已复核 |
| `page_aligned` | 页面已对齐 |
| 自动提取 | 自动提取，待复核 |
| 未知 | 验证状态未知 |

引用注册成功只表示来源和定位有效，不代表正式业务方案已经完成法务或业务确认。

## 7. 简化的数据流

```text
1. Agent 使用知识库 Skill 检索并复核原文
2. Agent 调用 tau_cite 注册准备使用的 knowledge_id
3. 系统把文档、页码、原文和状态保存在 toolResult.details
4. Agent 在最终回答中写 [[cite:knowledge_id]]
5. React 把标记显示为行内编号
6. React 根据 details 在消息末尾生成引用依据
7. 用户点击后，由服务端按 sourceId 打开受控原件
```

服务端只接受 `sourceId`，不接受浏览器传入任意文件路径。真实路径仍由知识库目录和文档元数据解析。

## 8. 两个实施阶段

### 阶段一：完成可用的引用板块（已实现）

这是主要阶段，完成后引用功能即可上线。

工作内容：

- 修正知识库 Skill 当前错误的脚本路径；
- 让知识库引用结果补齐标题、文档 ID、来源类型和必要定位；
- 增加 `tau_cite`，将可信引用写入 `toolResult.details`；
- 识别 Assistant 中的 `[[cite:...]]`；
- 实现正文编号；
- 实现消息末尾“引用依据”板块；
- 实现 PDF 定页、文档详情和图片缩略图；
- 支持刷新、历史和 resume；
- 处理引用缺失、未复核和原件变化。
- 允许 Agent 将当前任务目录中的报告、PDF、普通文档和图片注册为通用引用。

完成标准：

- 用户能从回答中的 `[1]` 找到消息末尾的对应来源；
- PDF 能打开到正确物理页；
- 文档能显示正确章节和引用原文；
- 图片能显示缩略图或整图入口；
- Agent 不能通过 Markdown 伪造本地文件路径；
- 刷新和恢复会话后引用仍然存在；
- 没有引用的普通消息不受影响。

### 阶段二：按真实需求增强定位

阶段一使用一段时间后，再根据实际材料决定是否实施：

- PDF 引用区域高亮；
- 图片局部区域高亮；
- OCR 置信度和扫描件提示；
- 用户上传附件后自动解析和索引；
- Markdown 脚注或报告导出。

阶段二不改变正文 Marker 和消息末尾引用板块，只增加更精确的定位能力。

## 9. 当前实现落点

阶段一沿用项目现有的 Contract、Extension、JSONL、Server 和 React 边界，没有引入数据库或第二套消息协议：

| 层 | 当前实现 |
|---|---|
| 共享契约 | `src/contracts/citation.ts` 定义 `pi-citation/1.0`，统一知识库和任务产物的来源、定位与引用记录 |
| 知识库 Skill | `search_knowledge.py cite --json` 返回标题、来源类型、相对路径和摘要；Skill 要求先核查再注册 |
| Agent 工具 | `extensions/pi-citation/` 提供 `tau_cite`，接收可信知识 ID 或当前任务内的报告、PDF、文档和图片 |
| 会话持久化 | 引用 Envelope 写入 `toolResult.details`，随 Pi JSONL 保存；前端从同一用户轮次内的工具结果恢复 |
| React 展示 | 正文 Marker 渲染为编号，消息末尾按来源分组，图片显示缩略图，复制时转换为普通来源列表 |
| 原件访问 | Server 按 live session、`sourceId`、真实路径边界和 SHA-256 校验提供只读内容 |

引用原件只能在 live 或 resume 后的会话中打开；纯历史快照仍能显示已保存的标题、定位和引文，但不会绕过 live session 的访问边界直接读取本机文件。

## 10. 异常与安全边界

以下情况必须有明确行为：

| 情况 | 处理 |
|---|---|
| 引用 ID 不存在 | `tau_cite` 拒绝注册 |
| 文档未通过知识库验收 | 拒绝注册 |
| 回答使用未注册 ID | 显示“引用不可用” |
| 原件丢失 | 保留标题、页码和引用原文，禁用打开 |
| 原件内容变化 | 提示“来源已更新” |
| PDF 无法预览 | 仍显示原文和页码 |
| 图片没有区域坐标 | 展示整张图片 |
| 流式输出只有半个引用标记 | 等待标记完整后再渲染 |
| 标记出现在代码块中 | 按普通代码显示，不解析 |

安全边界：

- 浏览器不接收知识库绝对路径；
- Agent 不能向引用工具传入任意路径；
- 服务端根据受信任 `sourceId` 解析文件；
- 文件必须位于配置的知识库目录；
- 引用标记继续经过现有 Markdown 转义和 HTML 清洗；
- PDF、图片和文档内容只读。

## 13. 最终逻辑线

这项功能可以归纳成一条简单路径：

```text
知识库给出可信 ID
    ↓
系统保存 ID 对应的来源和定位
    ↓
回答正文只显示引用编号
    ↓
消息末尾集中展示来源
    ↓
点击后查看原文
```

阶段一已经完成这条路径。阶段二只负责让 PDF 和图片定位得更精确，不阻塞当前引用板块使用。
