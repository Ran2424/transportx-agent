建议采纳的顺序

  1. 先做判断所需的数据入口。 第一版固定源版本、有效时间、ID 映射、规则版本和结果清单。结果保存原始秒数、时区、指标口径、空值语义和版本摘要，任务只使用被接受批次。
  2. 模块提供三项能力。 列出被接受版本，执行有界查询，导出可校审成果。继续复用 TransportX 当前任务、引用与 Canvas。缺证据、拒绝执行和明确不可用在返回结构里有各自状态。
  3. 按业务需要挂接专业引擎。 计划班次对比可先完成确定性查询。涉及地理路径与多站接续时接 OTP，保留图与服务覆盖。空间成果固定发布优先试 PMTiles，共享更新频繁再用 PostGIS/Martin 和版本固定的要素 API。协作部门已有相应客户端时再接 MCP 或 OGC Processes。
  4. 用留出样本验收反馈。 校审意见先当待验证假设。候选由证据和审批建立，再核阈值、缺失、版本和异常输入。实验中的 420→300 秒候选比较了 21 项合成样本，旧版仍可字节级重放。生产部署需要真实观察数据和独立验证。 反馈回放

失败和环境决定

开发 Web 模式拒绝安装模块，随后用桌面开发 Host 和单一模块的测试信任确认完成安装。一次引用轮询出现回环连接重置，一次重启等待 Pi 状态 RPC 超时。复跑只重读 GET，保留出错证据。不同本地模型、提示与工具内容见实际结果表。

数据库、API、路由与地图使用本机隔离服务。第三方引擎、空间 API 和分发样本各自有独立验证范围。真实数据只用于接入校验，仿真和反馈样本为合成。性能结果限于记录的本机样本、冷暖状态和并发级别。

使用现有本机 Ollama、Docker 与 Windows 运行时，额外拉取了 Qwen3.5 4B 和固定镜像。独立实验执行按 GPT-6.1 Terra high 分工，主会话档位由客户端控制。对外交付要按实际组合核对 TransportX 许可及数据授权。 TransportX 许可
